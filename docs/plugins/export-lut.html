导出 3D LUT

plugin/export-lut 调色 Color

lb:color-lookup 是「读 .cube」，这一支是反过来：把当前图层挂着的 非破坏滤镜栈，整个烘成一个 .cube。调好的色就能脱离这个工程单独走—— 给视频、给另一张图、给另一个软件，甚至给手机上的调色 App。

菜单位置
  • SuperMrWang → Export → 3D LUT…
  • 图层右键 → SuperMrWang → Export → 3D LUT…

这几条是同一个动作，处理的是当前选中的那一个图层。图层组不行——组没有自己的像素，会直接报错并提示先合并。

脚本调用
lb-plugin-export-lut(image, drawables)

这个命令必须开界面：LUT 尺寸与输出路径都在对话框里选，没有对应的过程参数；批量烘请直接调 lut_bake.py。

依赖

不依赖任何自研算子，也不用编译：只调 GIMP 自己的图层滤镜 API（复制图像、merge 滤镜、读像素），再按 .cube 的文本格式写文件。装了插件就能用；读回来验证时才需要 lb:color-lookup。

怎么用

三次点击

先在图层上用非破坏滤镜把色调到满意（菜单 Colors / Filters 里的 算子会以滤镜形式挂上去），再选 SuperMrWang → Export → 3D LUT…。 对话框里只问三件事：尺寸（17³ / 33³ / 65³）、输出路径， 以及确认一下顶部列出的算子清单。

尺寸越大越准、文件越大：17³ 是 4913 条，适合预览；33³ 是 35937 条， 一兆出头，绝大多数场合够用；65³ 是 274625 条，靠近黑场的折点才不失真， 文件约 8 MB。三者都是边长立方的整数格，不是随便切的采样。

没有滤镜的图层会被拦下来，并告诉你先去挂一个——空栈烘出来就是恒等 LUT，没有意义。

它烘的是什么

整条栈，不是一个算子

复制一份图像 → 只留目标层 → 在上面铺一张单位图 → 按滤镜栈从底到顶 逐条 merge → 读回像素。所以曲线 + 色阶 + 色相偏移这样叠了四五层的一串调整， 出来仍然只有一个 LUT。原图一个字节都不动。

单位图的排法是公开实现的通行做法：宽 size²、高 size， 像素 (x = g·size + r, y = b) 里存 (r,g,b)/(size−1)， 红变化最快。参考的是 RawTherapee 的 CubeLUT（PR #7676， HALD / .cube 导出）与 OpenColorIO 的 FileFormatIridasCube::bake()——表头 LUT_3D_SIZE、 六位小数、R 最快 B 最慢，都按它们的写法。

两个坑，都写进回归了

0.8 个色阶

① merge 顺序反了。get_filters() 是从栈顶往下给， 而 GIMP 实际先算栈底。照列表顺序 merge，等于把整条链倒着跑一遍—— 实测差 0.8 个色阶，肉眼不一定看得出，但和屏幕上看到的就是两张图。 必须 reversed()。

② 精度不能中途改。为了躲 8bit 量化，曾把副本转成浮点再烘——结果 管线语义变了：8bit 每一级都 clamp 到 0…1，浮点不 clamp，负的 a/b 会一路 带到下一级。同一份栈照样差 0.8。原图层什么精度就按什么精度烘。

哪些算子烘得准，哪些只是近似

LUT 是「像素值 → 像素值」的查表，所以逐像素算子能完整表示： 曲线、色阶、色相 / 饱和度、色彩平衡、通道混合、曝光、白平衡这一类， 烘出来和原栈逐格对得上。

看邻居像素的算子（高斯模糊、降噪、USM、置换、木偶 / 自由变形、 图层样式、最大最小值）以及多输入算子，LUT 只能拿一个像素去查， 几何和邻域信息根本不在表里。这些会在对话框里被标成「近似」并点名， 不会被悄悄咽下去。

图层带蒙版时会先在副本上把蒙版摘掉——蒙版让滤镜只作用在一部分像素上， 那种「同一输入两种输出」的东西本来就不是函数，烘出来没有意义。

烘完怎么验

贴回去比

最直接的一条：把 .cube 丢给 lb:color-lookup，挂在原图上， 和原来那条滤镜栈逐像素比。33³ 三线性的格间误差实测最大 0.040（出现在近黑的折点处），格点位置差 ≤ 1.5 码—— 曲线在暗部拐得越急，格与格之间那点线性插值的缺口越明显，这就是加尺寸的 理由。

回归 check_export_lut_gimp.py 33 项：单位图布局（红最快）、 恒等栈必须出恒等表、单滤镜逐格对账、三滤镜串联 vs 直接过栈、.cube 文本格式 （表头 / 行数 / 小数位 / 顺序）、空栈报错、原图逐字节未改、8bit 与浮点 各自对账。

非交互

这个命令必须开界面：尺寸和路径都要选，没有对应的过程参数。批量烘 （一条 LUT 给一组图）请在 GIMP 的 Python-Fu 里循环调用本模块的 lut_bake.bake() 与 write_cube()，那两件事与对话框 无关，可以直接用。

依赖：只需要 GIMP 自己的图层滤镜 API， 不需要任何自研算子模块，装了插件就能用。

Export 3D LUT

plugin/export-lut Color Color

lb:color-lookup reads a .cube; this one does the opposite. Whatever non-destructive filter stack the layer is carrying gets baked into a single .cube, so the grade can leave the project — to video, to another image, to another piece of software, even to a phone app.

Menu location
  • SuperMrWang → Export → 3D LUT…
  • Layer right-click → SuperMrWang → Export → 3D LUT…

These are all the same action, applied to the one layer you have selected. Layer groups do not work — a group has no pixels of its own, so the plug-in stops with an explicit error and asks you to merge first.

Scripting
lb-plugin-export-lut(image, drawables)

Needs the dialog: the LUT size and the output path are chosen there — there are no procedure arguments for them.

Dependencies

No operator modules and nothing to compile: it only drives GIMP's own layer-filter API (duplicate the image, merge each filter, read the pixels) and writes the .cube text format itself. Installing the plug-in is enough; lb:color-lookup is only needed if you want to load the result back to compare.

Three clicks

17³ / 33³ / 65³

Grade the layer with non-destructive filters first (operators from the Colors / Filters menus attach themselves as filters), then pick SuperMrWang → Export → 3D LUT…. The dialog asks for two things — size and output path — and lists the operators it found in the stack so you can confirm before writing.

Bigger is more accurate and bigger on disk: 17³ is 4,913 entries, fine for a preview; 33³ is 35,937, about a megabyte, and enough almost everywhere; 65³ is 274,625, roughly 8 MB, for grades that fold hard near black. All three are exact cubes — an integer grid per axis, not an arbitrary sample.

A layer with no filters is refused, with a message telling you to attach one first: an empty stack bakes an identity LUT, which is pointless.

What it actually bakes

the whole stack

Duplicate the image → keep only the target layer → lay an identity image on it → merge every filter from the bottom of the stack to the top → read the pixels back. So curves plus levels plus a hue shift — four or five layers of adjustment — still come out as one LUT. Not one pixel of the original is touched.

The identity image uses the layout both public implementations agree on: width size², height size, and pixel (x = g·size + r, y = b) holding (r,g,b)/(size−1), red varying fastest. The references are RawTherapee's CubeLUT (PR #7676, HALD / .cube export) and OpenColorIO's FileFormatIridasCube::bake() — LUT_3D_SIZE header, six decimals, R fastest and B slowest, all in their format.

Two traps, both in the regression

0.8 of a level

① Merging in the wrong order. get_filters() hands you the top of the stack first, while GIMP evaluates the bottom first. Merging in list order runs the whole chain backwards — measured at 0.8 of a level. Subtle, but it is still not the picture you saw on screen. It needs reversed().

② Changing precision halfway. To dodge 8-bit quantisation the copy was once converted to float before baking — which changes what the pipeline means: 8-bit clamps at every step to 0…1, float does not, so a negative a/b carries into the next filter. Still 0.8 apart. Bake at the layer's own precision.

Exact, or only approximate

A LUT is a pixel-in / pixel-out table, so per-pixel operators survive intact: curves, levels, hue / saturation, colour balance, channel mixer, exposure, white balance — the baked table matches the live stack grid point for grid point.

Neighbourhood operators (Gaussian blur, denoise, unsharp mask, displace, puppet / mesh warp, layer styles, max / min) and multi-input operators cannot be represented: a LUT looks up one pixel and has no geometry or neighbourhood in the table. The dialog labels these “approximate” and names them, rather than swallowing the discrepancy.

If the layer carries a mask, the mask is dropped on the copy first: a mask makes the filter apply to only some pixels, so the same input has two outputs — not a function, and not something a LUT can hold.

Checking the result

load it back

The direct test: hand the .cube to lb:color-lookup, put it on the same image and compare pixel by pixel. With 33³ and trilinear lookup the worst between-grid error measures 0.040 (near a hard fold in the shadows) while the grid points themselves land within 1.5 codes. The sharper the curve bends in the dark end, the more that gap between neighbouring entries shows — which is the reason to go up a size.

Regression check_export_lut_gimp.py, 33 checks: identity-image layout (red fastest), an identity stack must bake an identity table, per-filter grid reconciliation, three filters in series versus running the stack directly, .cube text format (header / row count / decimals / order), the empty-stack error, the original image byte-for-byte unchanged, and 8-bit and float each reconciled separately.

Not scriptable as a procedure

This command needs the dialog: size and path both have to be chosen, and there are no procedure arguments for them. To bake in bulk (one LUT applied to a folder), call lut_bake.bake() and write_cube() from Python-Fu in a loop — neither has anything to do with the dialog.

Dependencies: GIMP's own layer-filter API only. No operator modules from this project are needed — installing the plug-in is enough.
