消失点

plugin/vanishing-point 变形 Distort

这一支不拽像素，它是**给画面标一块「有透视的平面」**：拖一个四边形， 它就代表三维世界里的一块矩形；网格按世界坐标等距铺开，于是自然朝消失点收敛。 标好之后能往回拉——把整张图透视贴上去，或者把这块画面拉正成矩形；也能把这块 平面**折成一级级台阶**，同一张图沿台阶连续铺上去。

菜单位置
  • SuperMrWang → Distort → 消失点（透视平面）…

这几条是同一个动作，处理的是当前选中的那一个图层。图层组不行——组没有自己的像素，会直接报错并提示先合并。

脚本调用
lb-plugin-vanishing-point( image, drawables, planes, mode, along, output, stairs)

标准 PDB 过程，参数留空走默认值。

依赖

靠下面这些算子干活。它们已经打进这个插件的下载包（modules-windows-x64 / modules-linux-x64），不用另外去下：

怎么用

拖一个四边形

选图层 → 菜单 → 在画面上拖出一个四边形。这就是一块平面。拖它的四个角， 让它贴住真实的墙、地面或桌面——不用很准，网格会告诉你差多少。

选中平面后，每条边的中点有一个小三角，拖它就能从这条边再长出一块相邻 平面。方向有两种：「垂直于这块」（PS 的墙对墙）和「在同一平面里」 （同一面墙接着铺）。新平面的两条深度线自动指向垂直方向的消失点，所以不用手调 就接得上。

右侧两种活：透视贴图把整张图按四角铺到这个平面上，平面外一个字节都不动； 拉正反过来，把这块画面展开成一张新矩形图层——拍歪的海报、路牌、名片 就是这么救回来的。

从脚本

平面是 planes 参数：每个平面 8 个数，四个角按 「左上、右上、右下、左下」的顺序，多个平面用 | 隔开。第一个 是生效的那个，其余只是留着让对话框下次还能读回来。

lb-plugin-vanishing-point layer|
  planes="100,120,900,80,1020,700,60,780" mode=paste output=replace

只给 6 个数也行，第四角补成平行四边形。对话框按「应用」时会把用过的平面串写回 这个参数，所以手动拖出来的东西脚本能原样重放。

怎么算的

单应 + 垂心

四边形四角 ↔ 世界坐标的 (0,0)/(1,0)/(1,1)/(0,1)，八个参数用四点法解一个 8×8 线性方程组，得到单应矩阵 H。之后所有事都是 H 的正反用：

· 网格：世界里 s = k/N 的等距直线，逐条投影到图像上。所以网格是真的「等距」， 近处稀、远处密，收敛到消失点——不是画出来的装饰线。
· 贴图：源图四角 ↔ 平面四角，反解每个目标像素落在源图哪儿。
· 拉正：反过来，输出矩形的 (s,t) 经 H 找到源坐标。

第二面墙靠一条纯射影几何的事实：三个互相垂直方向的消失点，构成一个三角形， 而主点（画面中心）正是它的垂心。所以知道平面自己的两个消失点，第三个方向 不用相机内参、不用焦距就算得出来——只假设主点在画面正中。

折成台阶

同一张图沿台阶连铺

标好平面后勾上「折成台阶」，这块平面就沿一条边折成一级级台阶，图 沿台阶连续铺上去——不是每级各贴一份，而是整张图被折过去。起边 选折痕从哪条边起（远 / 近 / 右 / 左），级数 1–24，踢面高与 踏面深都是平面的比例；踏面深填 0 = 自动 = 1/级数，正好铺满平面。 踢面高取踏面深的一半左右最像真楼梯。

脚本里是 stairs="起边,级数,踢面高,踏面深,反向"，例如 stairs="0,6,0.075,0,0"；空串就是不起台阶。按「应用」时这一串 会写回参数。

为什么必须真三维

一块平面反解整台相机

第一版想省事：拼几个四边形凑出台阶。越往上级差得越远，第 6 级的边已经偏出 十几个像素——因为「抬高一个边长」在透视里不是「往下挪几个像素」，而是往 第三个维度走一步。

所以改成反解相机。一块有透视的平面其实把整台针孔相机都定死了：主点固定在 画面中心、像素是方的、两个消失点正交，于是 f² = −(Vu−O)·(Vv−O) 唯一给出焦距。b = K⁻¹·p 把三个 角换算到相机坐标，归一化得旋转 R，n = r1×r2 是法线， 相机位置 eye = −Rᵀ·b3。z 的单位是两边边长的几何平均—— b 本身就是「长度 × 方向」，不是纯方向（这一条算错过一次， 三维投影差到 278 px）。

台阶的三个坑

1. 没有透视的四边形解不出焦距。四边两组平行时（比如正对着拍的矩形）， 退回 f = 1.5 × 长边，状态行会写 approximate。这时正中间的踢面 正好侧对相机、退化成一条线，必须丢掉——不丢就是一条白缝，还会让单应 解奇异直接崩。

2. 图会上下反。源图第 0 行落在最近那一级上（v 沿台阶累加）， 所以海报要先上下翻一下才正——实测就是这么发现的。

3. 台阶会自己挡住自己。立起来的踢面盖住后面的踏面。取色判据必须按 「最后一个覆盖该点的面片」算，不然回归里会误判成贴错。

实测

1600×2400、16 面片：1.54 s；预览 560 长边 16 面片 172 ms/帧， 拖动跟得上。所有面片共用一块目标缓冲（numpy 里 arr / sarr 各只建一次），否则每贴一块面片就要重建 17 MB。

三个非踩不可的

1. 单应必须先用 Hartley 归一化。直接拿原始像素（上千的量级）解 8×8， 条件数能差到 1e8，纯 Python 的高斯消元只好到 1e-3——四边形一歪，贴图就错位。 归一化到「质心在原点、平均距离 √2」之后，残差回到 1e-13。

2. 网格线要按齐次分母 w 的符号断开。世界坐标往远处延伸时 w 会过零， 越过零点的那一段是「地平线之后」的像，跟前面的点连起来会画出一条横穿画面 的假线——看着像画面裂了一道。

3. 第三方向的消失点不是「另一组边的交点」。拿平面另一对边去求，得到的是 同一个消失点，墙会贴到墙自己身上。必须是垂心关系。

…还有两个

4. 延伸平面的两个远角不能取同一个 t。都写成 p + t·(V−p) 会让 新平面的上下两条边严格平行，u 方向消失点跑到 1e16 外面——等于把透视扔了。 正确解：q0 落在 p0 的射线上，q1 由「落在 p1 的射线上」和「q0q1 过共享边方向的 消失点」两条约束解出来。

5. 贴图的边界是硬边，拉正的边界会脏。贴图时平面外保持原样，所以边缘是 一刀切；拉正时输出顶边正好压在四边形边上，双线性会混进一点外面，实测差 3 个 色阶——肉眼看不出来，但回归里要把边界 6 px 排除掉，否则会误报。

实测

768×1024 图层：贴图 127 ms、拉正 71 ms。1600×2400： 贴图 635 ms、拉正 356 ms。比木偶变形慢，因为整块平面都要重采样； 但只算平面的外接框，比「整幅透视」省一半。

预览按 560 长边跑，一次约 75 ms，拖动跟得上手。纯 Python 那条路 大概慢 4 倍（1200×900 一秒钟），只在没装 numpy 时用。

和 PS 的差异

有：四边形平面、朝消失点收敛的透视网格、从边延伸相邻平面（垂直 / 延续 两种）、透视贴图、拉正成新图层、把平面折成 n 级台阶并沿台阶连续贴图。
没有：PS 最常用的那个「在平面上用图章/画笔，笔画自动贴合透视」——那要写 GIMP 的绘图工具类，工作量是另一件事，台阶上同理；也没有导出 3D、没有「平面 自动吸附共享消失点」（我们是靠拖角对齐）。台阶只有一段折（n 级同向）， PS 可以在一个平面里画好几段折线、中途拐弯，这一点还没做。

想对照着看：Krita 的「透视辅助线」是同一类东西（但只画线、不贴图）， 而真正的教科书名字叫 homography-based image transfer。

Vanishing Point

plugin/vanishing-point Distort Retouch

This one does not drag pixels around. It marks **a plane that has perspective** on the picture: drag out a quadrilateral and it stands for a rectangle in the 3D world. The grid is laid out at even spacing in world units, so it converges to the vanishing points by itself. Once the plane is marked you can use it in either direction — paste the whole picture into it, or rectify that patch back to a flat rectangle. You can also **fold the plane into steps** and have one picture run continuously up them.

Menu location
  • SuperMrWang → Distort → Vanishing Point（透视平面）…

These are all the same action, applied to the one layer you have selected. Layer groups do not work — a group has no pixels of its own, so the plug-in stops with an explicit error and asks you to merge first.

Scripting
lb-plugin-vanishing-point( image, drawables, planes, mode, along, output, stairs)

A standard PDB procedure; leave an argument empty to take its default.

Dependencies

The operators below do the work. They are already inside this plug-in's download (modules-windows-x64 / modules-linux-x64) — nothing else to fetch:

Using it

drag one quadrilateral

Pick a layer → menu → drag a quadrilateral on the picture. That is a plane. Drag its four corners until it sits on a real wall, floor or tabletop — it does not have to be exact, the grid shows you how far off you are.

With a plane selected, every edge carries a little triangle at its midpoint; drag it to grow a neighbouring plane from that edge. Two directions: perpendicular (Photoshop's wall-next-to-wall) and in the same plane (the same wall, further along). The new plane's depth lines point at the perpendicular vanishing point automatically, so it joins up without hand-tuning.

Two jobs on the right: paste into the plane lays the whole layer onto the quadrilateral, leaving everything outside untouched; rectify does the opposite and unfolds that patch into a flat rectangular layer — how you rescue a poster, street sign or business card shot at an angle.

From a script

The mesh is the planes argument: eight numbers per plane, four corners in the order top-left, top-right, bottom-right, bottom-left, planes separated by |. The first one is the one that acts; the rest are kept so the dialog can read them back next time.

lb-plugin-vanishing-point layer|
  planes="100,120,900,80,1020,700,60,780" mode=paste output=replace

Six numbers are enough too — the fourth corner is completed as a parallelogram. Pressing Apply writes the plane string back into this argument, so a script can replay a hand-dragged plane exactly.

How it is computed

homography + orthocentre

The four corners map to world (0,0)/(1,0)/(1,1)/(0,1); eight parameters, one 8×8 linear system, and you have a homography H. Everything after that is H used forwards or backwards:

· Grid — evenly spaced world lines s = k/N, projected one by one. So the grid really is evenly spaced in the world: wide near the camera, tight far away, converging to the vanishing points. It is not decoration.
· Paste — the source image's four corners map to the plane's four corners; every destination pixel is solved back to a source coordinate.
· Rectify — the reverse: each output pixel's (s,t) goes through H to find the source.

The second wall rests on one fact of projective geometry: the vanishing points of three mutually perpendicular directions form a triangle whose orthocentre is the principal point (the centre of the frame). So from a plane's own two vanishing points the third direction follows with no camera intrinsics and no focal length — the only assumption is that the principal point is in the middle.

Folding it into steps

one picture, continuous

Tick fold into steps and the plane folds along one edge into n treads and risers, with the picture running continuously up them — one copy folded over, not one copy per step. Choose the edge the fold starts from (far / near / right / left), the count (1–24), the riser and the run, both as fractions of the plane. Run 0 means "auto" = 1/count, which fills the plane exactly. A riser around half the run reads like a real staircase.

From a script: stairs="edge,count,riser,run,flip", for example stairs="0,6,0.075,0,0"; an empty string means no fold. Apply writes the string back into the argument.

Why it has to be real 3D

one plane solves the camera

The first attempt tried to be cheap: stitch a few quadrilaterals together into a staircase. The higher the step, the worse the drift — by step six the edge was off by a dozen pixels. Raising something by one side length is not "move it down a few pixels" in perspective; it is a step along the third axis.

So the camera is solved instead. A plane with perspective pins the whole pinhole camera: principal point at the centre of the frame, square pixels, orthogonal vanishing points, therefore f² = −(Vu−O)·(Vv−O) gives the focal length uniquely. Then b = K⁻¹·p brings three corners into camera space, normalising them gives the rotation R, n = r1×r2 is the normal and eye = −Rᵀ·b3 the position. The unit of z is the geometric mean of the two side lengths — b already carries length, it is not a pure direction (getting this wrong once put the 3D projection off by 278 px).

Three traps in the fold

1. A quad without perspective cannot yield a focal length. When both pairs of edges are parallel (a rectangle shot head-on), it falls back to f = 1.5 × long side and the status line says approximate. The riser in the middle is then edge-on to the camera and collapses to a line — it has to be dropped, or you get a white seam and a singular homography that aborts.

2. The picture comes out upside down. Source row 0 lands on the nearest step (v accumulates along the stairs), so a poster has to be flipped first. Found by looking at the render, not by reading the code.

3. Steps occlude themselves. A standing riser hides the tread behind it, so the sampling test has to use "the last face that covers this pixel" — otherwise the regression reports a mismatch that is not there.

Measured

1600×2400 with 16 faces: 1.54 s. Preview at a 560 px long edge, 16 faces: 172 ms per redraw, which keeps up with dragging. All faces share one destination buffer (arr / sarr are built once), otherwise every face rebuilds 17 MB.

Three things that quietly break it

1. The homography must be solved on Hartley-normalised points. Feeding raw pixel coordinates (thousands) into an 8×8 system puts the condition number near 1e8, and plain Gaussian elimination only lands at 1e-3 — nudge one corner and the paste is misaligned. Normalising to "centroid at the origin, mean distance √2" brings the residual back to 1e-13.

2. Grid lines must break where the homogeneous denominator changes sign. Extending the world outward makes w cross zero; past that point you are looking at the image behind the horizon, and joining it to the previous points draws a bogus line straight across the picture — it looks like the frame has been torn.

3. The third vanishing point is not "the intersection of the other pair of edges". Doing that returns the same vanishing point you started with and the wall lands on top of itself. It has to be the orthocentre relation.

…and two more

4. The two far corners of a grown plane must not share one t. Writing both as p + t·(V−p) makes the new plane's two edges exactly parallel and sends its u vanishing point out past 1e16 — perspective thrown away. The correct construction: q0 sits on p0's ray, and q1 comes from intersecting "on p1's ray" with "q0q1 passes through the shared edge's vanishing point".

5. Paste has a hard edge; rectify has a dirty one. Paste leaves the outside untouched, so the border is a clean cut. Rectify puts its first row exactly on the quadrilateral's edge, where bilinear sampling mixes in a little of the outside — measured at 3 levels, invisible to the eye, but the regression has to skip 6 px at the border or it reports a false failure.

Measured

768×1024 layer: paste 127 ms, rectify 71 ms. 1600×2400: paste 635 ms, rectify 356 ms. Slower than puppet warp because the whole plane is resampled — but only the plane's bounding box is touched, which halves the work compared with a full-frame perspective transform.

The preview runs at a 560 px long edge, about 75 ms per redraw, which keeps up with the drag. The pure-Python path is roughly 4× slower (one second at 1200×900) and only runs when numpy is missing.

Where it differs from Photoshop

Has: quadrilateral planes, a grid that converges to the vanishing points, growing a neighbouring plane from an edge (perpendicular or continuing), paste into the plane, rectify to a new layer, folding the plane into n steps with the picture running continuously over them.
Does not have: Photoshop's most-used trick — cloning and painting on the plane with the stroke following the perspective. That needs a GIMP paint tool subclass and is a job of its own — same for painting on the steps. Also no 3D export, and planes do not snap to each other's vanishing points (you align them by dragging corners). The fold is single-segment (n steps in one direction); Photoshop lets you draw several segments inside one plane and turn corners, which is not done here.

Worth comparing against: Krita's perspective assistants are the same idea but only draw guides, they do not transfer images. The textbook name for the transfer itself is homography-based image transfer.
