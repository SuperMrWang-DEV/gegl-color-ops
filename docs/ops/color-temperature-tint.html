Color Temperature & Tint

lb:color-temperature-tint 色彩 逐像素

经典图像编辑器 2026「色彩与自然饱和度」里的色温 / 色调：中性灰跟着偏蓝-黄、绿-洋红，黑白两端不动

按黑盒标定得到的 classic image editor 2026「色彩与自然饱和度」调整图层里的色温和色调两个滑块。经典图像编辑器 27.0 把这两个滑块塞进了原来的 vibrance 图层（官方名 Color and vibrance），Action Manager 里还是老的 vibrance 类，只是多带 temperature / tint 两个整数键，所以这里把白平衡部分单独拆成一个算子，便于叠加到任何管线里。

  • GEGL id：lb:color-temperature-tint
  • 菜单：Colors → SuperMrWang → Color → Color Temperature & Tint 经典图像编辑器
  • 类型：GeglOperationPointFilter（逐像素，无邻域）
  • 参数：temperature（−100…100，负冷正暖）、tint（−100…100，负绿正洋红）

算法

flowchart TD
  A["sRGB 编码值"] --> B["解码到线性光"]
  B --> C["居中到 [−1,1]：c' = 2c − 1"]
  C --> D["3 次多项式，20 项<br/>系数按 (色温, 色调) 在 17×17 网格上双线性插值"]
  D --> E["clamp 到 [0,1]"]
  E --> F["编码回 sRGB"]
  F --> G["烘焙进 33³ LUT（每张图一次）"]
$$c' = 2c-1,\qquad \text{out} = \operatorname{clamp}\!\left( \sum_{d=0}^{3}\ \sum_{\substack{i+j+k=d\\ i,j,k\ge0}} a_{ijk}(T,t)\;r'^{i}g'^{j}b'^{k},\ 0,\ 1\right)$$

$a_{ijk}(T,t)$ 是 17×17 参数网格上的双线性插值结果。

三个动作，每个都有明确来源：

步骤为什么
在线性域拟合编码域拟合时 经典图像编辑器的硬裁切只能被逼近成一团糊；实测负色温区域中位误差到过 90 码
clamp经典图像编辑器是「线性值被压到负数后切 0」。这是整条管线里唯一的强非线性，交给 clamp 精确复现，不要指望多项式
17×17 参数网格 + 双线性插值映射随 (色温, 色调) 变化很快，25 一档跨得太大（网格间误差 10–90 码）；加密到 12/13 一档后降到 1–5 码
烘成 33³ LUT逐像素算 20 项 + 两次 powf 太慢，一张图只烘一次

系数一共 17×17×20×3 = 17340 个数，在 common/temp-tint.h 里，由 tools/gen_temp_tint_tables.py 从 vibrance-cal/temp_tint_grid17_lin.json 生成 —— 要改数值请改上游数据再重新生成，不要手抄。

多项式顶点顺序与标定脚本的 terms() 一致：常数项，然后 d=1..3，每个 d 内按 i=0..d、j=0..d-i 枚举 r^i g^j b^(d-i-j)。输入先居中到 [−1,1] （r' = 2r−1），否则正规方程在 0..1 上病态，系数会解出上百倍。

标定方法

  1. vibrance-cal/make_probe_all.py 生成 32³ = 32768 色块的全色域探针 （1024×2048，横排 128 块，必须嵌 sRGB ICC，否则经典图像编辑器按工作空间解释后 饱和色会被裁，早期数据全废在这上面）。
  2. vibrance-cal/batch_vib2026.jsx 驱动经典图像编辑器2026 逐点套参数另存 PNG。
  3. vibrance-cal/fit_censored.py 对每个网格点拟合。截断样本（输出 0 或 255） 不含幅值信息但含「这一侧被削平」的信息，用带删失的迭代回归处理： 先在未截断样本上拟合，再把方向错的截断样本按铰链目标补进去重拟合。
  4. vibrance-cal/refit_lin17.py 跑完 289 个网格点，输出 JSON； tools/gen_temp_tint_tables.py 再生成头文件。

已知偏差

除最后一行那种角落，全平面中位误差 ≤ 5 码。角落里不是实现问题，是 经典图像编辑器 自己在那里不连续：

色温 ≤ −50 且色调 ≥ +38 的对角线上（大致 |色温| ≈ 色调 且都超过 55），经典图像编辑器 会让某个通道的线性值穿过 0，整通道从 255 塌到 0。实测同一块中性灰 (123,132,132)：

参数经典图像编辑器输出
(−62, 50)(122, 148, 239)
(−50, 62)(126, 140, 248)
(−62, 62)(117, 148, 0)
(−75, 75)(113, 152, 0)

也就是说相邻一格，结果不是「接近」而是「跨了一个台阶」。连续模型只能在插值时把两侧混起来，逐像素不可能复刻。要真补上，只能在网格上做局部细分（产品网格装不下非均匀细分，得整张加密到 6 一档 = 1089 点），收益不划算。

顺带记一下走过的弯路，免得以后重犯：这套映射不是线性矩阵（线性 sRGB 上最小二乘残差 p99 数十码）、不是通道独立（outR 对 G/B 的敏感度达 247 码）、不是可分离（M(60,60) ≠ M(tint60)·M(temp60)，误差 0.41）、不是在 Adobe RGB 里做三通道增益（内部样本中位 9.6–100 码）。多项式 + clamp 是目前唯一撑得住的形式。

性能

对整张图 temperature/tint 是常量：prepare() 插值系数、烘 33³ LUT （约 7 万次 powf，量级是毫秒），process() 只剩每像素 8 次查表 + 7 次乘加。恒等参数直接 memcpy，不碰像素。

与 lb:vibrance 的关系

经典图像编辑器 2026 的「色彩与自然饱和度」是先色温色调、再 Vibrance的顺序（实验依据：把色温处理后的图喂给经典图像编辑器2025 的纯 Vibrance，与经典图像编辑器一次调完的结果中位差 1.4 码；顺序反了差 36 码）。

两个算子在工程里是分工的，不互相调用：本算子只做白平衡，lb:vibrance 只做 Vibrance。要复刻经典图像编辑器2026 那个图层，把本算子叠在 lb:vibrance 前面即可 ——

lb:color-temperature-tint  →  lb:vibrance

顺序由图层栈承担，所以两边的参数表各只有一份，白平衡结果与单独跑本算子逐位相同。

只要这一个

Windows 模块 color-temperature-tint.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 color-temperature-tint.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。这里的每个模块都是独立的 GEGL 模块，只链接 GIMP 自带的 GEGL 与 babl，不依赖本项目里的其它模块——下这一个就够用，不会缺东西。要一次装齐，用整包。

Color Temperature & Tint the classic editor

lb:color-temperature-tint Color per-pixel

The temperature and tint sliders from classic image editor 2026's Color and Vibrance layer, matched by black-box measurement into a 33³ LUT.

The temperature and tint sliders of classic image editor 2026's Color and vibrance adjustment layer, matched by black-box measurement. the classic editor 27.0 folded both sliders into the old vibrance layer (officially "Color and vibrance"); the Action Manager still uses the old vibrance class with two extra integer keys, temperature and tint. The white-balance part is split out into its own operator so it can be stacked into any pipeline.

  • GEGL id: lb:color-temperature-tint
  • Menu: Colors → SuperMrWang → Color → Color Temperature & Tint the classic editor
  • Type: GeglOperationPointFilter (per-pixel, no neighbourhood)
  • Parameters: temperature (−100…100, negative = cooler), tint (−100…100, negative = green, positive = magenta)

Algorithm

flowchart TD
  A["sRGB encoded"] --> B["decode to linear"]
  B --> C["centre to [−1,1]: c' = 2c − 1"]
  C --> D["cubic polynomial, 20 terms<br/>coefficients bilinear over a 17×17 (temperature, tint) grid"]
  D --> E["clamp to [0,1]"]
  E --> F["encode back to sRGB"]
  F --> G["bake into a 33³ LUT (once per image)"]
$$c' = 2c-1,\qquad \text{out} = \operatorname{clamp}\!\left( \sum_{d=0}^{3}\ \sum_{\substack{i+j+k=d\\ i,j,k\ge0}} a_{ijk}(T,t)\;r'^{i}g'^{j}b'^{k},\ 0,\ 1\right)$$

$a_{ijk}(T,t)$ is the bilinear interpolation of the 17×17 parameter grid.

Three decisions, each with a reason:

StepWhy
fit in the linear domainfitting in the encoded domain can only smear the classic editor's hard clipping into mush; the negative-temperature region was measured at a median error of 90 code values
the clampthe classic editor clips linear values that go negative to 0. This is the only strong non-linearity in the chain; reproduce it exactly with a clamp instead of expecting a polynomial to do it
17×17 parameter grid + bilinearthe map changes quickly with (temperature, tint); steps of 25 were far too coarse (10–90 code values between grid points), while 12–13 brings it down to 1–5
bake into a 33³ LUT20 terms plus two powf per pixel is slow; bake once per image

That is 17×17×20×3 = 17340 coefficients in common/temp-tint.h, generated by tools/gen_temp_tint_tables.py from vibrance-cal/temp_tint_grid17_lin.json — change the upstream data and regenerate, never hand-edit.

Polynomial term order matches the calibration script's terms(): the constant term, then d=1..3 with i=0..d, j=0..d-i enumerating r^i g^j b^(d-i-j). Inputs are centred to [−1,1] first (r' = 2r−1); otherwise the normal equations are ill-conditioned on 0..1 and the coefficients blow up by two orders of magnitude.

Calibration method

  1. vibrance-cal/make_probe_all.py builds a full-gamut probe of 32³ = 32768 patches (1024×2048, 128 per row). It must embed an sRGB ICC profile, otherwise the classic editor interprets it in the working space and clips saturated colours — early data was lost entirely to this.
  2. vibrance-cal/batch_vib2026.jsx drives the classic editor 2026 to apply each setting and save a PNG.
  3. vibrance-cal/fit_censored.py fits every grid point. Clipped samples (output 0 or
    1. carry no magnitude but do carry "this side got flattened", which is handled by
    iterative regression with censoring: fit on unclipped samples first, then add misdirected clipped samples back through a hinge target and refit.
  4. vibrance-cal/refit_lin17.py runs all 289 grid points and writes JSON; tools/gen_temp_tint_tables.py turns that into the header.

Known deviations

Outside that last corner the median error over the whole plane is ≤ 5 code values. The corner is not an implementation problem — the classic editor itself is discontinuous there:

On the diagonal where temperature ≤ −50 and tint ≥ +38 (roughly |temperature| ≈ tint, both above 55) the classic editor pushes one channel's linear value through zero and the whole channel collapses from 255 to 0. Measured on the same neutral grey (123,132,132):

Settingthe classic editor output
(−62, 50)(122, 148, 239)
(−50, 62)(126, 140, 248)
(−62, 62)(117, 148, 0)
(−75, 75)(113, 152, 0)

One grid step apart, the result is not "close" but "a step across the cliff". A continuous model can only blend the two sides when interpolating; per-pixel reproduction is impossible. Truly fixing it would need local subdivision of the grid (the product grid cannot hold non-uniform subdivision, so the whole thing would have to be refined to steps of 6 = 1089 points), which is not worth it.

Worth recording the dead ends so they are not repeated: this map is not a linear matrix (least-squares residual on linear sRGB is tens of code values at p99), not channel-independent (outR responds to G/B by up to 247 code values), not separable (M(60,60) ≠ M(tint60)·M(temp60), error 0.41), and not a three-channel gain in Adobe RGB (median 9.6–100 code values on internal samples). Polynomial plus clamp is the only form that holds up so far.

Performance

For a whole image temperature/tint are constant: prepare() interpolates the coefficients and bakes a 33³ LUT (about 70k powf, milliseconds), leaving process() with 8 lookups and 7 multiply-adds per pixel. Identity settings memcpy and never touch the pixels.

Relation to lb:vibrance

the classic editor 2026's Color and vibrance applies temperature/tint first, then Vibrance (experimental basis: feeding the temperature-processed image into the classic editor 2025's plain Vibrance differs from the classic editor doing both at once by a median of 1.4 code values; the reverse order differs by 36).

The two operators divide the work and do not call each other: this one does white balance only, lb:vibrance does Vibrance only. To reproduce the the classic editor 2026 layer, stack this one in front of lb:vibrance:

lb:color-temperature-tint  →  lb:vibrance

The order is carried by the layer stack, so each side keeps one parameter table and the white-balance result is bit-identical to running this operator alone.
