Vibrance

lb:vibrance 色彩 逐像素

按 经典图像编辑器「自然饱和度」的实测响应改饱和度：低饱和吃得饱、高饱和主动收手、红带（肤色）额外保护、浅色少给一点，色相与明度不动

按黑盒标定得到的 经典图像编辑器的「自然饱和度」，不是凭经验的近似。同一张标定图分别过经典图像编辑器 26.10 和本算子，像素级逐位对比见文末「验收」。

  • GEGL id：lb:vibrance
  • 菜单：Colors → SuperMrWang → Color → Vibrance
  • 类型：GeglOperationPointFilter（逐像素，无邻域）
  • 参数：vibrance（−100…100）、protect_reds、compensate_lightness

只管 Vibrance，色温色调不在这里

经典图像编辑器 2026（27.0）把自然饱和度图层改名成「色彩与自然饱和度」，多出色温 / 色调两个滑块，动作上就是先一层白平衡、再走原来的 Vibrance。

本工程不把这两段揉进一个算子：色温 / 色调由独立的 lb:color-temperature-tint 负责， lb:vibrance 只做 Vibrance 本身。想复刻「色彩与自然饱和度」，按顺序叠两层即可：

图层 / 滤镜栈：  色温色调（lb:color-temperature-tint）  →  Vibrance（lb:vibrance）

要 2025 的纯 Vibrance，把底下那层删掉就是。这样拆的好处：

  • 两个算子各有一个滑块职责，界面上不会出现「这个色温到底管整层还是只管这段」；
  • 顺序由图层栈显式表达（经典图像编辑器的顺序是白平衡在前，实测中位差 1.4 码；反过来差 36 码）， 想换顺序就换图层顺序，不用再来回勾开关；
  • 白平衡的结果和 lb:color-temperature-tint 单跑逐位相同，不存在两套代码 各自漂移的问题。

算法

在 sRGB 编码值（R~G~B~A float，感知域而非线性光）上转 HSV，按源图饱和度 S 取增量：

$$\Delta S = A(v)\,S^{p(v)}\,(1-S)^{q(v)}\,r(H,S,v)\,c(L),\qquad S' = \min(1,\ S+\Delta S)$$
项含义数据来源
A(v)、p(v)、q(v)幅度与两端曲率，随 v 逐档查表16 位 / 步长 5 标定，20 档
r(H,S,v)红带（离红色 40° 以内）的额外压制；26°–40° 线性过渡出去同 v 下 H0 与 H120 的比值
c(L)亮度修正：浅色少给（L=80 只有 0.72 倍，L=20 有 1.39 倍）E 段 L 阶梯

RGB 重建：保持 max 不动，其余通道按 $S'/S$ 缩放：

$$\text{out}_{ch} = m_x - \bigl(m_x - c_{ch}\bigr)\frac{S'}{S}$$

—— out = mx − (mx − c)·S'/S。因为 mx − mn = S·mx，当 S' ≤ 1 时最小通道恰好落在 [0, mx]，数学上不会越界，不需要任何裁剪或色域收敛。

负方向（v<0）是另一套机制，不是正向的镜像：实测结果是 S 降、V 也会跟着降，而且没有色相项，所以直接用两张表（S' 与 V'/V），同样按 (v, S) 双线性插值。

参数表在 vibrance-tables.h 里，由 tools/gen_vibrance_tables.py 从 vibrance-cal/vibrance_model.json 生成 —— 要改数值请改上游 JSON 再重新生成，不要手抄。

性能

v 对整张图是常量，所以每条随 v 变化的曲线都在 prepare() 里先折叠成一行（11 个采样点），process() 只剩一维查表和两次 powf。全图 1080×880 的标定图用 gegl CLI 渲染约 0.2 s（含 PNG 编解码）。

两层叠加的「色彩与自然饱和度」组合验收（对经典图像编辑器2026 实测）与色温色调本身的精度，见 ops/color-temperature-tint/README.md —— 那里有 v/t/n 七组参数的中位/p90/p99/最大偏差，以及色温 ≤ −50 且色调 ≥ +38 对角线上经典图像编辑器硬裁切造成的已知偏差。

已知偏差

拟合残差只在采样点上成立（A 段 ΔS 残差 0.41 pp @ v=+100），整图上的大头在两处标定维度没覆盖到的地方：

  1. 红带里 H≈17° 的橙/肤色（B 段，L62）：r 只按 H0 拟合，H17 处经典图像编辑器压得更狠。 v=+60 时该段中位偏差 2.9 码、v=+100 时 8.4 码（最大 14.8）。
  2. 负方向在浅色上的明度变化（E 段）：V'/V 表只在 L=50 上拟合，L=80 时 经典图像编辑器 实际压得比表里小得多（该处最大偏差 29 码，sRGB 下是肉眼可见的变暗）。

这两处都不是实现问题，是模型维度不够（色相只有 6 个采样点、明度 5 档）。要补，方向是做 probe v2：L×S 网格 + 5° 色相细扫，然后重拟合 r(H,S,v) 与负向的 V'(S,L,v)。

与 lb:vibrance-hyper 的关系

vibrance-hyper 是 LAB 域的外观建模（色度双曲蒙版 + 肤色窗 + 色域收敛），调出来的手感好、参数可解释，但不保证和经典图像编辑器数值一致。 vibrance 是数值复刻：和经典图像编辑器对得上，但没有可调的艺术性参数。两个并存，按需要选。

只要这一个

Windows 模块 vibrance.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 vibrance.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。这里的每个模块都是独立的 GEGL 模块，只链接 GIMP 自带的 GEGL 与 babl，不依赖本项目里的其它模块——下这一个就够用，不会缺东西。要一次装齐，用整包。

Vibrance

lb:vibrance Color per-pixel

The classic editor's Vibrance, matched by black-box measurement — measured tables, red-band protection, lightness compensation, and no white balance mixed in.

the classic editor's Vibrance, matched by black-box measurement rather than approximated. The same calibration chart was pushed through the classic editor 26.10 and through this operator; the pixel-level comparison is in the acceptance section.

  • GEGL id: lb:vibrance
  • Menu: Colors → SuperMrWang → Color → Vibrance
  • Type: GeglOperationPointFilter (per-pixel, no neighbourhood)
  • Parameters: vibrance (−100…100), protect_reds, compensate_lightness

Vibrance only — temperature and tint are elsewhere

the classic editor 2026 (27.0) renamed the Vibrance layer to "Color and vibrance" and added temperature / tint sliders, which action-wise are one white-balance layer followed by the old Vibrance.

This project does not fuse the two into one operator: lb:color-temperature-tint owns temperature/tint and lb:vibrance does Vibrance alone. To reproduce "Color and vibrance", stack two layers in order:

layer / filter stack:  Color Temperature & Tint (lb:color-temperature-tint)  →  Vibrance (lb:vibrance)

For 2025's plain Vibrance, delete the lower layer. Why split it:

  • each operator has one slider's worth of responsibility, so there is never a question of "does temperature act on the whole layer or only this segment";
  • the order is expressed by the layer stack (the classic editor's order is white balance first — measured median difference 1.4 code values; reversed it is 36), and changing it means reordering layers instead of unticking a box;
  • the white-balance result is bit-identical to running lb:color-temperature-tint alone, so there are not two implementations drifting apart.

Algorithm

Convert to HSV on sRGB encoded values (R~G~B~A float, the perceptual domain, not linear light) and derive an increment from the source saturation S:

$$\Delta S = A(v)\,S^{p(v)}\,(1-S)^{q(v)}\,r(H,S,v)\,c(L),\qquad S' = \min(1,\ S+\Delta S)$$
TermMeaningData source
A(v), p(v), q(v)amplitude and the curvature at both ends, per step of v16-bit calibration in steps of 5, 20 steps
r(H,S,v)extra suppression in the red band (within 40° of red), fading linearly out from 26° to 40°ratio of H0 to H120 at the same v
c(L)lightness correction: give less to light colours (0.72× at L=80, 1.39× at L=20)the L ladder of segment E

RGB reconstruction: keep max fixed and scale the other channels by $S'/S$:

$$\text{out}_{ch} = m_x - \bigl(m_x - c_{ch}\bigr)\frac{S'}{S}$$

channel lands exactly in [0, mx], so the maths cannot leave the gamut and no clipping or gamut mapping is needed.

The negative direction (v<0) is a different mechanism, not a mirror of the positive one: measurements show S drops and V drops with it, and there is no hue term, so it uses two tables (S' and V'/V), also bilinearly interpolated over (v, S).

The tables live in vibrance-tables.h, generated by tools/gen_vibrance_tables.py from vibrance-cal/vibrance_model.json — change the JSON and regenerate, never hand-edit.

Performance

v is constant over the image, so every curve that varies with v is folded into one row (11 samples) in prepare(), leaving process() with a 1D lookup and two powf. The 1080×880 calibration chart renders in about 0.2 s through the gegl CLI including PNG encode/decode.

v=0 is bit-identical, so the colour pipeline (linear↔encoded round trip) does not secretly touch pixels. The C implementation matches the Python reference in vibrance-cal/vibrance_ref.py pixel for pixel (≤1 code, pure rounding).

The two-layer "Color and vibrance" acceptance against the classic editor 2026, and the accuracy of the temperature/tint part, are in ops/color-temperature-tint/README.md — median/p90/p99/max over seven v/t/n combinations, plus the known deviation on the diagonal where temperature ≤ −50 and tint ≥ +38 and the classic editor clips hard.

Known deviations

The fit residual only holds at the sampled points (segment A's ΔS residual is 0.41 pp at v=+100); on a real image the bulk of the error sits in two places the calibration grid did not cover:

  1. Orange and skin tones near H≈17° inside the red band (segment B, L62): r was fitted on H0 only, and the classic editor suppresses H17 harder. At v=+60 that segment is off by a median of 2.9 code values, 8.4 at v=+100 (max 14.8).
  2. The negative direction's lightness change on light colours (segment E): the V'/V table was fitted at L=50 only, and at L=80 the classic editor presses much less than the table does (up to 29 code values there — a visible darkening in sRGB).

Neither is an implementation bug: the model has too few dimensions (six hue samples, five lightness steps). The fix would be a probe v2 — an L×S grid plus a 5° hue sweep — and a refit of r(H,S,v) and of the negative V'(S,L,v).

Relation to lb:vibrance-hyper

vibrance-hyper is an appearance model in Lab (hyperbolic chroma mask, skin window, gamut mapping): pleasant to use with explainable parameters, but not guaranteed to match the classic editor numerically. vibrance is the numerical reproduction: it matches the classic editor, but has no artistic parameters. Both exist; pick by need.
