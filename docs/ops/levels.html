Levels

lb:levels 影调与色阶 逐像素

PS 色阶：复合 + R/G/B 四组「输入黑场 / 灰点 / 白场 + 输出黑场 /白场」，数值刻度 0–255，与 PS 对话框的数字框一一对应

PS「色阶」对话框的复刻：复合 + R/G/B 四组，每组都是 「输入黑场 / 输入灰点 / 输入白场 + 输出黑场 / 输出白场」五个数， 刻度 0–255，和 PS 的数字框一一对应。

对应面板：Colors → SuperMrWang → Tone → Levels。

模型

单通道：

t   = clamp((v - inLow) / (inHigh - inLow), 0, 1)
t'  = t ^ (1 / gamma)
out = outLow + t' * (outHigh - outLow)
  • inLow 及以下压成 outLow，inHigh 及以上压成 outHigh， 中间按 gamma 曲线重新分布；
  • gamma > 1 提亮，gamma < 1 压暗（与 PS 数字框同向。注意这与 「标准 gamma」的直觉相反，因为 PS 的滑块值直接进的是 1/gamma 的倒数位置； 指数写成 t^gamma 会让方向整个反过来）；
  • 输入区间会把整段拉伸：设了 inLow = 64 之后，v = 240 会变成 235， 不是原样保留；
  • inHigh == inLow 时区间塌成一点，按台阶处理（≥ 该值为白），不除零。

执行顺序：先复合组（三通道同一条曲线），再各通道组。各通道组默认恒等， 所以「只动复合」与 PS 的 RGB 通道模式逐位一致；「只动红」等价于 PS 的 Red 通道模式。四组可以叠加使用，这比 PS 一次只能选一个通道更强。

域

在 8bit sRGB 伽马域逐通道直接算，不回线性光。色阶的黑白场是 「0–255 编码值」的语义，喂线性光会让数字框对不上 PS。算子自己在 prepare 里把两个 pad 钉成感知格式（R~G~B~A float），不需要前置 linear-rgb。

本机为什么没做逐码标定

PS 2025（26.10.0）在这台机器上：executeAction 的 Lvls 事件、以及 Mk 创建调整图层，都直接抛「不能完成命令，因为程序错误」；DOM 的 LayerKind.LEVELS 也给「只能改为文本或正常」。诊断日志见 ../lvls-cal/_diag2.txt。colorRange 反而能跑，所以不是 ExtendScript 整体 不可用，是这两个命令在这套安装里被挡了。

因此基准改用公开实测值，而不是本机标定。如果你在另一台机器上能跑 PS 脚本， 可以把 lvls-cal/ 里的 ps_levels.jsx 修好重跑，就能升级成逐码标定。

与 GIMP 自带「色阶」的区别

GIMP 的 Colors → Levels 是 app 层私有实现，GEGL 里的 gegl:levels 只有 in-low / in-high / out-low / out-high 四个属性——没有 gamma，没有每通道， 也没有 0–255 的数字刻度（gegl --info gegl:levels 可查）。所以这个算子补的是 GEGL 算子层面的真空白：脚本、批处理、gegl 命令行里都能用 PS 的色阶参数。

Levels

lb:levels Tone per-pixel

Photoshop's Levels dialog — composite plus R/G/B, five numbers each, 0–255 scale, with PS's gamma direction.

A reproduction of Photoshop's Levels dialog: composite plus R/G/B, four groups of five numbers each — input black, input grey, input white, output black, output white — on a 0–255 scale that matches PS's numeric fields one for one.

Panel: Colors → SuperMrWang → Tone → Levels.

Model

Per channel:

t   = clamp((v - inLow) / (inHigh - inLow), 0, 1)
t'  = t ^ (1 / gamma)
out = outLow + t' * (outHigh - outLow)
  • inLow and below is crushed to outLow, inHigh and above to outHigh, and the middle is redistributed along the gamma curve;
  • gamma > 1 brightens, gamma < 1 darkens — the same direction as PS's field. Note this is the opposite of the usual gamma intuition: PS's slider value goes straight into the reciprocal position of 1/gamma, and writing the exponent as t^gamma flips the whole direction;
  • the input range stretches everything: after setting inLow = 64, v = 240 becomes 235 rather than staying put;
  • when inHigh == inLow the range collapses to a point and is handled as a step (anything ≥ that value is white) instead of dividing by zero.

Order: the composite group first (one curve for all three channels), then the per-channel groups. Per-channel groups default to identity, so "touch only the composite" is bit-identical to PS's RGB mode and "touch only red" matches PS's Red channel mode. All four groups can be stacked, which is more than PS allows (one channel at a time).

Domain

Everything is computed per channel in the 8-bit sRGB gamma domain, never decoded to linear. Levels' black and white points mean "0–255 encoded values", and feeding linear light would make the numeric fields disagree with PS. The operator pins both pads to a perceptual format (R~G~B~A float) in prepare, so no upstream linear-rgb is needed.

These matter: a test that only checks "C agrees with Python" cannot catch a reversed exponent, because both sides would be wrong together. The values come from a measured pixel posted in Adobe's community and the accepted out = in^(1/gamma).

Why there is no per-code calibration on this machine

On this machine, Photoshop 2025 (26.10.0) throws "could not complete the command because of a program error" for both the Lvls executeAction event and Mk adjustment-layer creation, and the DOM's LayerKind.LEVELS only offers text-or-normal. The diagnostic log is in ../lvls-cal/_diag2.txt. colorRange does run, so ExtendScript as a whole is fine — those two commands are blocked in this installation.

Hence the reference is public measurements rather than local calibration. If you can run PS scripts on another machine, fix ps_levels.jsx in lvls-cal/ and re-run it, and this can be upgraded to a per-code calibration.

Difference from GIMP's own Levels

GIMP's Colors → Levels is a private app-level implementation, and GEGL's gegl:levels has only four properties — in-low / in-high / out-low / out-high — with no gamma, no per-channel groups and no 0–255 scale (check gegl --info gegl:levels). This operator fills a genuine hole at the GEGL level: PS levels parameters now work from scripts, batch jobs and the gegl command line.
