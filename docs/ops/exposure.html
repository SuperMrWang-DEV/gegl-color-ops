Exposure EV

lb:exposure 影调 整块区域

经典图像编辑器 曝光：EV、偏移、伽马三段式调整（按 EV 计曝光档位）the classic editor Exposure: EV, offset and gamma in three stages, measured inexposure stops.

两条公式，按输入精度自动选路

precision 属性：auto（默认）/ encoded（强制 8 位）/ linear（强制 32 位）。 auto 读输入 pad 的源格式：整数格式（u8 / u16）走分支一，浮点格式 （float / half / double）走分支二。16 位图同样是伽马编码，所以和 8 位共用 分支一。

分支一：整数格式（sRGB 伽马编码值）

v1 = min(c · 2^(EV/2.2), 1)
v2 = clamp(v1^2.2 + offset, 0, 1)^(1/2.2)
v3 = v2^(1/gamma)

在伽马域乘 2^(EV/2.2) 与线性光乘 2^EV 完全等价，省掉两次幂运算；offset 是线性光下的量，所以中间解一次 2.2、加完再编码回去。

min(…, 1) 不能省。 先切高光再叠 offset，负 offset 才能把过曝区拉回来； 漏掉这步，EV>0 配负 offset 会把整片亮区顶成死白。旧版实现漏了这一行。

分支二：浮点格式（线性光）

v1 = c · 2^EV + offset
v2 = clamp(v1, 0, ∞)^(1/gamma)

输入已是线性光，没有 2.2 往返；曝光就是一次乘法，offset 直接相加。

与 Java 版的一处差别：Java 末尾有 clamp(…, 0, 1)，本算子只钳下限。 32 位图允许 HDR，按 0…1 截断会把高光压平；负值必须钳掉，否则 pow 出 NaN。

验收

python tools/check_exposure.py

12 组参数（EV −3…+2、offset ±0.15、gamma 0.45…2.2）× 64 级灰阶：

  • 分支一对拍 Java exposureChannel：最大 0.00 码
  • 分支二对拍 Java exposureChannel2：最大 0.00 码
  • 整数 PNG 输入下 auto 与 encoded 逐像素完全相同（0 处不同）
  • 浮点 EXR 输入下 auto 与 linear 完全相同，与 encoded 在 2944 个像素上不同 —— 说明 auto 真的切了分支，而不只是多了个开关

算法

同一套 EV 与 offset，按输入精度分两条路径。precision=auto 读输入 pad 的格式： 整数格式（u8 / u16）走编码域，浮点格式（float / half / double）走线性域； 16 位图同样是伽马编码的，和 8 位同路。

整数格式（sRGB 编码值）：先在编码域乘 $2^{EV/2.2}$（等价于线性域乘 $2^{EV}$， 但省掉两次幂运算），再解码、加线性域的 offset、编码回去：

$$v_1 = \min\!\left(c\cdot 2^{EV/2.2},\ 1\right),\qquad v_2 = \operatorname{clamp}\!\left(v_1^{2.2} + o,\ 0,\ 1\right)^{1/2.2},\qquad v_3 = v_2^{\,1/\gamma}$$

那个 $\min(\cdot,1)$ 不能省：先裁高光、再加 offset，负 offset 才能把过曝的高光拉回来； 去掉它，$EV>0$ 配负 offset 会把整片亮部推成纯白。

浮点格式（线性光）：输入已是线性，只需一次乘法与一次加法：

$$v_1 = c\cdot 2^{EV} + o,\qquad v_2 = \bigl(\max(v_1,\,0)\bigr)^{1/\gamma}$$

只夹下界、不夹上界：32 位图允许 HDR，裁到 $0..1$ 会把高光压平；但负值必须夹， 否则 pow 会返回 NaN。

Exposure EV

lb:exposure Tone area

The classic editor's Exposure adjustment with two formulas — 8-bit sRGB and 32-bit linear — chosen automatically from the input precision.

Menu: Colors → SuperMrWang → Tone → Exposure EV

Two formulas, picked from the input precision

precision property: auto (default) / encoded (force the 8-bit path) / linear (force the 32-bit path). auto reads the source format of the input pad: integer formats (u8 / u16) take branch one, float formats (float / half / double) take branch two. 16-bit images are gamma-encoded as well, so they share branch one with 8-bit.

Branch one: integer formats (sRGB gamma-encoded values)

$$v_1 = \min\!\left(c\cdot 2^{EV/2.2},\ 1\right),\qquad v_2 = \operatorname{clamp}\!\left(v_1^{2.2} + o,\ 0,\ 1\right)^{1/2.2},\qquad v_3 = v_2^{\,1/\gamma}$$

Multiplying by 2^(EV/2.2) in the gamma domain is exactly equivalent to multiplying by 2^EV in linear light and saves two exponentiations; offset is a linear-light quantity, hence the single decode to 2.2 in the middle and the re-encode afterwards.

The min(…, 1) cannot be dropped. Highlights are clipped first and the offset is added afterwards, which is what lets a negative offset pull blown highlights back. Skip it and EV>0 with a negative offset pushes the whole bright region to solid white. The old implementation was missing this line.

Branch two: float formats (linear light)

$$v_1 = c\cdot 2^{EV} + o,\qquad v_2 = \bigl(\max(v_1,\,0)\bigr)^{1/\gamma}$$

The input is already linear, so there is no 2.2 round trip; exposure is one multiply and the offset is added directly.

One difference from the Java version: Java ends with clamp(…, 0, 1), this operator only clamps the lower bound. 32-bit images allow HDR, and truncating to 0…1 would flatten the highlights; negative values must be clamped or pow returns NaN.

Acceptance

python tools/check_exposure.py

12 parameter sets (EV −3…+2, offset ±0.15, gamma 0.45…2.2) × 64 grey levels:

  • branch one against Java's exposureChannel: max 0.00 code values
  • branch two against Java's exposureChannel2: max 0.00 code values
  • with an integer PNG, auto and encoded are pixel-identical (0 differences)
  • with a float EXR, auto and linear are identical and differ from encoded on 2944 pixels — proof that auto really switches branches rather than adding an inert switch
