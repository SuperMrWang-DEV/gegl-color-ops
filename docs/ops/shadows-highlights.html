Shadows/Highlights

lb:shadows-highlights 影调 整块区域 不推荐Not recommended

不推荐日常使用　邻域双边加 4 次高斯，半径 30 时每像素约 1.4 µs：2048×1536 默认参数净耗时 0.7 s、含解码 2.1 s，在 GIMP 里拖一次滑杆就重算一遍整图。整体明暗改用 色阶 / LAB 色阶；确实需要「周围亮就少提」的局部行为再回来用它，半径压到 10–15 会快很多。详见 ops/shadows-highlights/.discouraged。

等价于经典图像编辑器「图像 → 调整 → 阴影/高光」：按邻域亮度分别提亮阴影、压暗高光，而不是只看像素值本身。

不推荐日常使用（2026-11-15，性能原因）　算子仍然可用、数值也仍然准确， 但它是空间域算法：半径 30 时每像素约 1.4 µs，2048×1536 默认参数净耗时 0.7 s （含解码 2.1 s），在 GIMP 里拖一次滑杆就重算整图。整体明暗请用 lb:levels / lb:lab-levels / lb:exposure；确实需要「周围亮就少提」的局部行为再用它， 半径压到 10–15 会快很多。标记文件：ops/shadows-highlights/.discouraged （只影响文档与站点展示，不影响编译和发布）。

按黑盒标定得到的 经典图像编辑器的「图像 → 调整 → 阴影/高光」。和另外十几个算子的最大 区别是它看邻域：同样一个 128 的像素，周围暗就多提、周围亮就少提，所以不可能简化 成一条 LUT，必须做空间域滤波。

  • GEGL id：lb:shadows-highlights
  • 菜单：Colors → SuperMrWang → Tone → Shadows/Highlights
  • 类型：GeglOperationFilter（空间域，按 192 行一条带处理）
  • 参数（默认值照抄 经典图像编辑器）：阴影 amount 35 / width 50 / radius 30、高光 0 / 50 / 30、 color-correction 20、midtone-contrast 0、black-clip 0.01、white-clip 0.01

先记一个坑：经典图像编辑器的脚本入口不叫 Shadow/Highlight

想把 经典图像编辑器 当 oracle，第一步是能用脚本调起它。Shdw、ShHl、shadowsHighlights、 shadowHighlight、adaptCorrectTones … 13 个 charID 加 8 个 stringID 轮流试， 全部报「命令<未知的>当前不可用」，编辑器进程 和 Required/*.dll 里也搜不到 shadowsHighlights 字样。

真正的入口是 adaptCorrect，类名 adaptCorrectTones：

var d = new ActionDescriptor();
d.putObject(s2t("shadowMode"),    s2t("adaptCorrectTones"), tones(sh));
d.putObject(s2t("highlightMode"), s2t("adaptCorrectTones"), tones(hi));
d.putDouble (s2t("blackClip"), 0.01);
d.putDouble (s2t("whiteClip"), 0.01);
d.putInteger(s2t("colorCorrection"), 20);
executeAction(s2t("adaptCorrect"), d, DialogModes.NO);

shadowMode/highlightMode 里再放 amount/width/radius（#Prc），其余键都是 stringID 小写。这条线索来自 官方用户社区一个 Clean SL 脚本，比盲试 ID 快得多。

算法结构

六个阶段，数全部来自 经典图像编辑器 25.4 的黑盒拟合（同一结构见 PhotoCraft，MIT）：

  1. 亮度：最大通道与 Rec.601 亮度的平均，直接作用在 sRGB 编码值上 （不是线性光）。这解释了为什么暗部提亮后颜色会发灰——它动的是显示值：
$$y = \tfrac{1}{2}\bigl(\max(R,G,B) + 0.299R + 0.587G + 0.114B\bigr)$$
  1. 邻域亮度 边缘感知双边，Durand–Dorsey 的分段线性形式：
    • 先把 lum 按 σ=1.3559 轻模糊成 guide（只为了抗噪，不决定尺度）；
    • 像素按 guide 量化到 17 级，每级用权重 w = 1 − |lum − g|/1.0152 单独加权平均；
    • 权重和 / 加权和在 d = ⌊σ/4⌋ 的格子上先累加，再用 σ = 1.1424·radius 的高斯模糊；
    • 最后按 guide 的小数级在相邻两级间插值，双线性上采样回全分辨率。

这么做等价于「只和亮度相近的邻居平均」，所以边缘两侧各算各的，不会互相污染。

  1. 色调遮罩 把 nb 当自变量查 256 项表，表 = 1 − BetaCDF(level)。形状随 「色调宽度」在 Beta(a,b) 之间线性插值：宽度 0 → Beta(1.95, 23)（只有最暗一小段）， 宽度 ≥95 → 1 − L（全线）。高光用 255 − nb 的镜像。
  2. 曲线 自屏幕 $c_q(v) = 1-(1-v)^q$，$q \in \{1,2,4,8\}$ 按「数量」$A$ 混合：
$$u = \left(\frac{A}{100}\right)^{0.6216},\qquad s = \begin{cases} u/0.3, & u \le 0.3 \\[4pt] (1+20u)/7, & u > 0.3 \end{cases} \qquad\Longrightarrow\qquad A = 15 \approx 1,\ 50 \approx 2,\ 100 \approx 3$$

阴影把每个通道抬 $m\cdot s\,\bigl(c_q(y)-y\bigr)$，高光用镜像压回。

  1. 颜色 只保留结果的新亮度 y2；色差取原像素 q 与它自己亮度 y1 之差， 按 exp(k·|ΔY|/maxY)（负值 1 + k·|ΔY|/maxY）缩放后加回，并统一收进色域。
  2. 中间调对比度 亮度上的全局 S 曲线 y + k(y−0.5)(4y(1−y))^p，支点恰在 0.5； 修剪黑/白 是直方图两端的拉伸。
flowchart TD
  A["sRGB 编码值"] --> B["亮度 y = (max + Rec.601) / 2"]
  B --> C["边缘感知双边：17 级量化 + 高斯，得 nb"]
  C --> D["色调遮罩 m = 1 − BetaCDF(nb)"]
  D --> E["自屏幕曲线 1−(1−v)^q<br/>按数量在 q=1/2/4/8 间混合"]
  E --> F["只留新亮度 y2<br/>原色差按 exp(k·|ΔY|/maxY) 加回"]
  F --> G["中间调对比度 + 黑白场修剪"]
  G --> H["输出"]

五、六两步写成式子：

$$\text{out}_{ch} = y_2 + (q_{ch}-y_1)\cdot \begin{cases} \exp\!\bigl(k\,|\Delta Y|/\max Y\bigr), & \Delta Y \ge 0 \\[6pt] 1 + k\,|\Delta Y|/\max Y, & \Delta Y < 0 \end{cases} \qquad y'' = y_2 + k\,(y_2-0.5)\bigl(4y_2(1-y_2)\bigr)^p$$

两个反直觉的实测结论

默认的 0.01% 修剪真的会改变画面。 一开始用 16 条灰带（16…240）做探针， 首尾两条总被拉到 0/255，误以为是算子串色。实际是 blackClip/whiteClip 的百分比 是相对直方图的：探针没覆盖 0 和 255，0.01% 就把最暗那条当成黑场拉下去了。 换成覆盖 0 与 255 的 129 条 ramp 后假象消失；对照组 a100/clip0 vs a100/clip01 上黑块 0 vs 7、背景 91 vs 87，差得很清楚。

半径改的不是模糊宽度，是「邻域里亮像素的占比」。 阶跃边（左 12 右 240）上， 半径从 0 加到 100，远离边缘的平台值单调 73 → 65，而紧贴亮边的那个像素一直是 48–50。 这说明边缘感知权重把亮邻居的贡献压到 ~12%，所以过渡只有 1–2 像素宽；半径变大只是 把更多亮像素拉进窗口，缓慢抬高 nb。用纯高斯直觉去调 σ 是调不对的。

性能

平场部分只有 256 项查表，开销全在邻域：17 级 × 4 次高斯。用 192 行条带限制内存， ramp-2.png（25800×160，129 条带）3.2 s，grid-b016.png（2560×2560）4.7 s， 都是含 PNG 编解码的墙钟时间。半径 30 时每像素约 1.4 µs。

二、和 经典图像编辑器 本身（shadows-highlights-cal/）：

已知偏差

  1. 极端局部对比的二维格点（20×20 小块压在 99% 面积的极端背景上， bg=16 配亮块、bg=240 配暗块）最大差 11 码。平场对得上、只有这种「邻域和 像素值差 200 码以上」的合成图案对不上，说明邻域核的边缘保持强度还差一点： 实测 经典图像编辑器的 nb 比本算子更贴近像素自身。把 SH_RANGE 从 1.0152 往下调（边缘保持 更强）会让 87% 的点变好但制造出 87 码的爆点；往上调（4.0 / 50，趋近纯高斯） 则单调变差。1.0152 是实测的局部最优值，所以保持原样，这个尾巴留着。
  2. h_a100_w0 的 5.7 码：色调宽度 0 时遮罩退化成 Beta(1.95, 23) 在最暗一段的 陡壁，插值表按宽度每 5 一档建，宽度 0 正好落在第一个节点上，误差最敏感。
  3. 半径 > 300 没标定：经典图像编辑器 对话框上限 2500，标定只做到 300，更大半径按同一 σ=1.1424·r 外推。
  4. midtone_contrast 与 color_correction 用的是参考实现的拟合系数，没有单独做 经典图像编辑器 实测（平场和彩色平场只验证了算子与参考实现一致，不是与 经典图像编辑器 一致）。

性能（2026-11-12 重构）

卡顿的三个根因，全部修掉：

  1. GEGL 按列并行，margin 随调用次数线性重复。3M 像素被拆成 12 根 171 宽的 竖条同时跑，每根竖条各带完整的水平 margin——r30 重复 2.4×，r300（margin 1277 px）重复 17×。修复：整个 extent 的邻域亮度只算一次，缓存成 8 位层级平面（遮罩查表用 lv = lround(clamp(nb)·255)，8 位量化无损）， 各列直接采样。缓存在参数变化（prepare 比较）、输入内容变化（24 行整行 哈希指纹，能察觉下层涂改）、几何变化三种情况下失效。
  2. 黑/白修剪的预扫把整条管线跑两遍。默认 0.01/0.01 就触发。缓存路径下 预扫改用现成的层级平面，只剩轻量逐像素。
  3. 逐行 gegl_buffer_set。每条 192 行调 192 次写；改为整条/整 ROI 一次写。

实测（2048×1536，含 PNG 解码 ~1.3s）：默认参数 3.7s → 2.1s；r300 9.8s → 2.1s （净耗时 7.9s → 0.7s，~11×）。数值与旧实现逐位一致（4 组极端参数下 缓存路径 = 回退路径 = 旧实现三方对拍）。

超大图或 margin 超预算（SH_CACHE_MAXPX 20MP / SH_CACHE_BUDGET）自动回落 到按条带就地计算；SH_NO_CACHE=1 环境变量可强制走回退路径（调试用）。 条带高度按 margin 自适应（4×margin，192–1024 行），亮度取数分块 （≈32MB/块）控峰值内存。

the classic editor's Image → Adjustments → Shadows/Highlights, matched as a black box. What sets it apart from the other operators is that it looks at the neighbourhood: the same 128 pixel is lifted more when its surroundings are dark and less when they are bright, so it cannot collapse into a LUT and needs a spatial filter.

  • GEGL id: lb:shadows-highlights
  • Menu: Colors → SuperMrWang → Tone → Shadows/Highlights
  • Type: GeglOperationFilter (spatial, processed in strips of 192 rows)
  • Parameters (defaults copied from the classic editor): shadows amount 35 / width 50 / radius 30, highlights 0 / 50 / 30, color-correction 20, midtone-contrast 0, black-clip 0.01, white-clip 0.01

One trap first: the classic editor's scripting entry is not called Shadow/Highlight

To use the classic editor as an oracle you first have to be able to invoke it from a script. Shdw, ShHl, shadowsHighlights, shadowHighlight, adaptCorrectTones … 13 charIDs and 8 stringIDs, all reporting "command <unknown> is not currently available", and the string shadowsHighlights does not appear anywhere in the editor process or Required/*.dll.

The real entry is adaptCorrect, class adaptCorrectTones:

var d = new ActionDescriptor();
d.putObject(s2t("shadowMode"),    s2t("adaptCorrectTones"), tones(sh));
d.putObject(s2t("highlightMode"), s2t("adaptCorrectTones"), tones(hi));
d.putDouble (s2t("blackClip"), 0.01);
d.putDouble (s2t("whiteClip"), 0.01);
d.putInteger(s2t("colorCorrection"), 20);
executeAction(s2t("adaptCorrect"), d, DialogModes.NO);

shadowMode/highlightMode then hold amount/width/radius (#Prc), everything else being lowercase stringIDs. The lead came from a Clean SL script in the vendor's community and was far faster than guessing IDs.

Structure

Six stages, all numbers from black-box fitting against the classic editor 25.4 (PhotoCraft uses the same structure, MIT):

  1. Luminance: the mean of the max channel and Rec.601 luma, applied to sRGB encoded values (not linear light). That is why lifting the shadows makes colours look washed out — it moves display values:
$$y = \tfrac{1}{2}\bigl(\max(R,G,B) + 0.299R + 0.587G + 0.114B\bigr)$$
  1. Neighbourhood luminance: an edge-aware bilateral in Durand–Dorsey's piecewise linear form. lum is first blurred lightly (σ=1.3559) into a guide (noise suppression only; it does not set the scale); pixels are quantised into 17 levels by guide, each level averaged separately with weight w = 1 − |lum − g|/1.0152; sums are accumulated on a grid of d = ⌊σ/4⌋ and blurred with a Gaussian of σ = 1.1424·radius; finally the fractional level interpolates between neighbouring levels and is bilinearly upsampled to full resolution. The effect is "average only with neighbours of similar brightness", so the two sides of an edge stay separate.
  2. Tonal mask: nb indexes a 256-entry table 1 − BetaCDF(level). The shape interpolates between Beta(a,b) by tonal width: 0 → Beta(1.95, 23) (only the darkest sliver), ≥95 → 1 − L (everything). Highlights mirror it with 255 − nb.
  3. Curve: a self-screen $c_q(v) = 1-(1-v)^q$, with $q \in \{1,2,4,8\}$ blended by amount $A$:
$$u = \left(\frac{A}{100}\right)^{0.6216},\qquad s = \begin{cases} u/0.3, & u \le 0.3 \\[4pt] (1+20u)/7, & u > 0.3 \end{cases} \qquad\Longrightarrow\qquad A = 15 \approx 1,\ 50 \approx 2,\ 100 \approx 3$$

Shadows lift each channel by $m\cdot s\,\bigl(c_q(y)-y\bigr)$; highlights push back with the mirror.

  1. Colour: keep only the new luminance y2; the chroma difference comes from the original pixel q minus its own luminance y1, scaled by exp(k·|ΔY|/maxY) (for negative values 1 + k·|ΔY|/maxY) and added back, then everything is brought into gamut.
  2. Midtone contrast: a global S-curve on luminance, y + k(y−0.5)(4y(1−y))^p, pivoting exactly at 0.5; black/white clip is a stretch of the histogram ends.
flowchart TD
  A["sRGB encoded values"] --> B["luminance y = (max + Rec.601) / 2"]
  B --> C["edge-aware bilateral: 17 levels + Gaussian → nb"]
  C --> D["tonal mask m = 1 − BetaCDF(nb)"]
  D --> E["self-screen 1−(1−v)^q<br/>blended over q = 1/2/4/8"]
  E --> F["keep new luminance y2<br/>restore chroma by exp(k·|ΔY|/maxY)"]
  F --> G["midtone contrast + black / white clip"]
  G --> H["out"]

Stages five and six as formulas:

$$\text{out}_{ch} = y_2 + (q_{ch}-y_1)\cdot \begin{cases} \exp\!\bigl(k\,|\Delta Y|/\max Y\bigr), & \Delta Y \ge 0 \\[6pt] 1 + k\,|\Delta Y|/\max Y, & \Delta Y < 0 \end{cases} \qquad y'' = y_2 + k\,(y_2-0.5)\bigl(4y_2(1-y_2)\bigr)^p$$

Two counter-intuitive measurements

The default 0.01% clip really does change the picture. The first probe used 16 grey bands (16…240); the outer two were always pulled to 0/255, which looked like crosstalk. In fact blackClip/whiteClip percentages are relative to the histogram: the probe had no 0 or 255, so 0.01% treated the darkest band as the black point. A 129-band ramp that includes 0 and 255 removed the artefact; the control pair a100/clip0 vs a100/clip01 shows black patch 0 vs 7 and background 91 vs 87, plainly.

Radius does not change the blur width, but the fraction of bright pixels in the neighbourhood. On a step edge (12 on the left, 240 on the right), raising the radius from 0 to 100 moves the plateau far from the edge monotonically from 73 to 65, while the pixel right at the bright edge stays at 48–50. The edge-aware weight suppresses bright neighbours to about 12%, so the transition is only 1–2 pixels wide; a larger radius just pulls more bright pixels into the window and slowly raises nb. Tuning σ by pure Gaussian intuition does not work.

Performance

The flat-field part is a 256-entry lookup; the cost is all in the neighbourhood: 17 levels × 4 Gaussian passes. 192-row strips bound the memory: ramp-2.png (25800×160, 129 bands) takes 3.2 s and grid-b016.png (2560×2560) 4.7 s, both wall-clock including PNG encode/decode. About 1.4 µs per pixel at radius 30.

Known deviations

  1. 2D grids with extreme local contrast (a 20×20 patch on a background covering 99% of the area, bg=16 with a bright patch and bg=240 with a dark one) are off by up to 11 code values. Flat fields agree and only these synthetic patterns — where the neighbourhood differs from the pixel by 200 code values or more — do not, which says the edge preservation is slightly too weak: the classic editor's nb sticks closer to the pixel itself. Lowering SH_RANGE below 1.0152 (stronger edge preservation) improves 87% of points but creates 87-code outliers; raising it (4.0 / 50, toward a plain Gaussian) only gets worse. 1.0152 is the measured local optimum, so it stays and this tail remains.
  2. The 5.7 codes of h_a100_w0: at tonal width 0 the mask degenerates to Beta(1.95, 23), a steep wall in the darkest segment; the lookup table is built in steps of 5 in width, and width 0 sits exactly on the first node where the error is most sensitive.
  3. Radius > 300 is not calibrated: the classic editor's dialog goes to 2500, calibration stopped at 300, and larger radii extrapolate with the same σ = 1.1424·r.
  4. midtone_contrast and color_correction use the reference implementation's fitted coefficients and were not measured against the classic editor separately (the flat and colour flat tests only prove the operator agrees with the reference, not with the classic editor).

Reproducing the calibration

shadows-highlights-cal/ holds the whole set: apply_cases.jsx (the classic editor-side runner), run_cases.py (batch run + read results), make_ramp.py / make_grid.py (three probe sets: greyscale bands, 2D grid, step edge), compare_op.py (per-point comparison), dump_grid.py / analyze_nb.py (single-case residuals and neighbourhood back-solving), sweep.py (neighbourhood-scale sweep).

Performance (rewritten 2026-11-12)

Three root causes of the sluggishness, all fixed:

  1. GEGL parallelises by column and the margin is repeated per call. 3M pixels were split into 12 vertical strips 171 wide running at once, each carrying the full horizontal margin — 2.4× duplication at r30 and 17× at r300 (margin 1277 px). Fix: compute the neighbourhood luminance of the whole extent once, cache it as an 8-bit level plane (the mask lookup uses lv = lround(clamp(nb)·255), lossless at 8 bits), and let each column sample it. The cache invalidates on parameter change (compared in prepare), on content change (24-row whole-row hash fingerprints, which catch edits to the layer below) and on geometry change.
  2. The black/white clip pre-scan ran the whole pipeline twice. The default 0.01/0.01 triggered it. With the cache, the pre-scan reuses the level plane and only does a light per-pixel pass.
  3. Per-row gegl_buffer_set. Each 192-row strip called it 192 times; now a strip or ROI is written in one call.

Measured (2048×1536, including ~1.3 s PNG decode): defaults 3.7 s → 2.1 s; r300 9.8 s → 2.1 s (compute 7.9 s → 0.7 s, ~11×). Numbers are bit-identical to the old implementation (four extreme parameter sets cross-checked: cache path = fallback path = old implementation).

Very large images, or a margin over budget (SH_CACHE_MAXPX 20MP / SH_CACHE_BUDGET), fall back to in-place per-strip computation; SH_NO_CACHE=1 forces the fallback (for debugging). Strip height adapts to the margin (4×margin, 192–1024 rows) and luminance is fetched in chunks (~32 MB each) to bound peak memory.

Just this one

Windows module shadows-highlights.dll, drop it into %LOCALAPPDATA%\gegl-0.4\plug-ins; Linux module shadows-highlights.so, drop it into ~/.local/share/gegl-0.4/plug-ins, then restart GIMP. Every module here is a standalone GEGL module: it links only against the GEGL and babl that ship with GIMP, never against another module of this project, so one download is all it needs.
