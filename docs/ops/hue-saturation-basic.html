Hue/Saturation (Basic)

lb:hue-saturation-basic 色彩 逐像素

三滑杆公式：全局色相旋转、饱和度相对缩放、明度向白/黑混合。

三滑杆版本：全局色相旋转、饱和度相对缩放、明度向白/黑混合。不含「着色」复选框， 也没有分色相区间。行为上与常见图像软件的「色相/饱和度」对话框三根滑杆一致。

  • GEGL id：lb:hue-saturation-basic
  • 菜单：Colors → SuperMrWang → Color → Hue/Saturation (Basic)
  • 类型：GeglOperationPointFilter（逐像素，无邻域）
  • 参数：hue（−180…180°）、saturation（−100…100）、lightness（−100…100）

2026-11-16：显示名从 Hue/Saturation (经典图像编辑器) 改为 Hue/Saturation (Basic)，菜单 标签同步。GEGL id 仍是 lb:hue-saturation-basic，已存在的 XCF / 过滤器栈不受影响。

规范实现是 tools/ref_hue_sat_basic.py（原代码的逐字转录 + 浮点对照）， 验收脚本是 tools/check_hue_saturation_basic.py。

算法

在 sRGB 编码值（R~G~B~A float，感知域而非线性光）上，四步：

t = lightness / 100
r,g,b ← c + t·(1−c)   (t > 0)      # 与中性灰做滤色
        c·(1+t)       (t < 0)      # 与中性灰做正片叠底
h,s,l ← RGB2HSL(r,g,b)
h ← (h + hue) mod 360
x = saturation / 100
s ← s/(1−x)  (x > 0)                # 双曲放大
    s·(1+x)  (x < 0)                # 线性收缩
s ← clamp(s, 0, 1)
out = HSL2RGB(h, s, l)

顺序有意义：明度先落进 RGB，再把结果转 HSL 做色相与饱和度 —— 所以饱和度作用在 「提亮/压暗之后」的 S 上，而不是原图的 S。

与原代码的两处差别

两处都不是算法语义，是实现缺陷：

差别原代码本算子理由
精度h 取整到 1°、s/l 取整到 1%，输出 int() 截断全程浮点这层量化平均偏暗 1.73 码、最大 9 码（tools/ref_hue_sat_basic.py 的 breakdown）
saturation=+100s/(1−1) → ZeroDivisionError返回满饱和（s>0 时）x→1⁻ 时 s/(1−x)→+∞，钳位后就是 1，取左极限

验收

python tools/check_hue_saturation_basic.py     # 27 组参数 × 4096 色
python tools/ref_hue_sat_basic.py              # 量化误差拆解
python tools/analyze_hue_sat_basic.py          # 三条曲线的行为体检

对拍结果：最大偏差 0.002 码（16 位 1 LSB = 0.0039 码），即与公式逐码一致； 脚本同时打印「与输入的平均差」，防止读到原图的假通过。

公式的合理性

成立的地方

  1. 明度滑杆不碰色相。 两个分支都是均匀仿射 c ↦ k·c + b，色相只由通道差值之 比决定，实测 Δh 恒为 0。同时它是单调的、端点精确（+100 全白、−100 全黑）、 不溢出 —— 比「直接改 HSL 的 L」在亮端会硬顶成白色要稳。
  2. 端点干净。 −100 精确到中性灰，+100 精确到满饱和，两个方向都收敛到有意义的 颜色，没有反相或跳变。
  3. 顺序符合直觉。 先定调子（明度），再定色彩强度（饱和度），且饱和度看到的是 提亮后的 S，避免了「先加饱和再提亮导致过曝」的常见问题。
  4. 无越界路径。 HSL→RGB 天然保色域，S 钳到 [0,1]，任何参数组合都不会输出非法值。

不成立的地方

  1. 正支刻度与标签不符。 正向乘数是 1/(1−x)，不是 1+x：+25 实际是 ×1.33 （+33%），+50 是 ×2（+100%），+90 是 ×10。负支才是名副其实的百分比 （−50 就是 ×0.5）。同一根滑杆左右两侧的量纲因此不对称。
  2. 正支有「悬崖」，会丢层次。 s ≥ 1−x 的像素一律钳到 100：+50 时原 S≥50% 的一半像素塌成同一个值，+100 时所有彩色像素统一满饱和，等价于把饱和度二值化。 表现为平坦色块与色带。
  3. 明度对 S 的影响强烈不对称。 +60 会把 (100,30,10) 的 S 从 82% 压到 23%， 而 −60 一字不动（82%）。用户预期「只改明度」，实际提亮会明显掉饱和、发灰。
  4. HSL 的 S 不是感知量。 同一 S 在黄色与蓝色上的视觉强度差很多，所以同一档位 在不同色相上表现不一致。这是 HSL 模型的固有问题，本公式无法规避。
  5. 量化损失（原代码）。 1% 的 s/l 台阶单这一项就有最大 8 码、平均 −1.25 码的 偏差，且系统性偏暗 —— 这是 8 位整数实现的代价，不是算法的一部分。

Hue/Saturation (Basic)

lb:hue-saturation-basic Color per-pixel

Three sliders — global hue rotation, relative saturation scaling, lightness mixed toward white or black. No Colorize, no hue ranges.

The three-slider variant: global hue rotation, relative saturation scaling, and lightness mixed toward white or black. No Colorize checkbox and no per-hue ranges. Behaviour matches the three sliders of the familiar Hue/Saturation dialog.

  • GEGL id: lb:hue-saturation-basic
  • Menu: Colors → SuperMrWang → Color → Hue/Saturation (Basic)
  • Type: GeglOperationPointFilter (per-pixel, no neighbourhood)
  • Parameters: hue (−180…180°), saturation (−100…100), lightness (−100…100)

The specification lives in tools/ref_hue_sat_basic.py (a literal transcription of the original code plus a float comparison), and the acceptance script is tools/check_hue_saturation_basic.py.

Algorithm

On sRGB encoded values (R~G~B~A float, the perceptual domain, not linear light), in four steps:

t = lightness / 100
r,g,b <- c + t·(1−c)   (t > 0)      # screen with neutral grey
         c·(1+t)       (t < 0)      # multiply with neutral grey
h,s,l <- RGB2HSL(r,g,b)
h <- (h + hue) mod 360
x = saturation / 100
s <- s/(1−x)  (x > 0)                # hyperbolic expansion
     s·(1+x)  (x < 0)                # linear contraction
s <- clamp(s, 0, 1)
out = HSL2RGB(h, s, l)

The order matters: lightness lands in RGB first, then the result is converted to HSL for hue and saturation — so saturation acts on the post-lightness S, not on the original one.

Two differences from the original code

Neither is about what the algorithm means; both are implementation defects:

DifferenceOriginalHereWhy
Precisionh rounded to 1°, s/l to 1%, output truncated with int()all floatthat quantisation is 1.73 code values dark on average, 9 at worst (see the breakdown in tools/ref_hue_sat_basic.py)
saturation=+100s/(1−1) → ZeroDivisionErrorfull saturation (when s>0)as x→1⁻, s/(1−x)→+∞, which clamps to 1 — the left limit

Acceptance

python tools/check_hue_saturation_basic.py     # 27 parameter sets × 4096 colours
python tools/ref_hue_sat_basic.py              # quantisation-error breakdown
python tools/analyze_hue_sat_basic.py          # behaviour checks on the three curves

Result: max deviation 0.002 code values (one 16-bit LSB is 0.0039), i.e. code-exact against the formula. The script also prints the mean difference from the input, so it cannot pass by accidentally reading the source image back.

Is the formula reasonable?

What holds up

  1. The lightness slider never touches hue. Both branches are uniform affine maps c ↦ k·c + b, and hue depends only on the ratio of channel differences; the measured Δh is always 0. It is also monotone, exact at the ends (+100 white, −100 black) and never overflows — steadier than editing HSL's L, which slams into white at the top.
  2. Clean endpoints. −100 lands exactly on neutral grey, +100 on full saturation; both directions converge to meaningful colours with no inversion or jump.
  3. The order is intuitive. Set the tone (lightness) first, then the colour strength (saturation), and saturation sees the brightened S — avoiding the classic "saturate then brighten and blow out" problem.
  4. No out-of-gamut path. HSL→RGB keeps the gamut by construction and S is clamped to [0,1], so no parameter combination emits an illegal value.

What does not

  1. The positive side's scale does not match its label. The positive multiplier is 1/(1−x), not 1+x: +25 is ×1.33 (+33%), +50 is ×2 (+100%), +90 is ×10. Only the negative side is an honest percentage (−50 is ×0.5). The two halves of the same slider are on different scales.
  2. The positive side has a cliff and loses detail. Every pixel with s ≥ 1−x clamps to 100: at +50 half of all pixels with S≥50% collapse onto one value, and at +100 every coloured pixel becomes fully saturated — saturation binarisation, in effect. It shows up as flat patches and banding.
  3. Lightness affects S very asymmetrically. +60 pushes the S of (100,30,10) from 82% down to 23%, while −60 leaves it at 82%. You asked for lightness; brightening also visibly desaturates and greys the image.
  4. HSL's S is not perceptual. The same S looks very different on yellow and on blue, so one setting behaves differently across hues. Inherent to the HSL model; the formula cannot avoid it.
  5. Quantisation loss (original code). The 1% s/l steps alone cost up to 8 code values and −1.25 on average, systematically dark — the price of an 8-bit integer implementation, not part of the algorithm.
