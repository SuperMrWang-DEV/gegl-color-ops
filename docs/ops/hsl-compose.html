HSL Compose

lb:hsl-compose 分量 整块区域

HSL 分量曲线工作流的合成器：把「R = 饱和度、G = 明度、B = 色相/360」的数据图还原成真实颜色

把数据图还原成真实颜色：R = 饱和度、G = 明度、B = 色相/360（都是 0…1），输出对应的 HSL 颜色，alpha 恒为 1。

(R=S, G=L, B=H/360) ──lb:hsl-compose──> 真实颜色

输入约定是硬的

本算子无法分辨输入是一张数据图还是一张普通照片——它一律按「R 是饱和度、G 是明度、B 是色相」解释。挂错地方会把照片当成数据算出一张乱七八糟的图。

正常用法是紧跟在 lb:hsl-dual 之后（中间夹两条曲线）：

lb:hsl-dual → S 曲线(红) → L 曲线(绿) → lb:hsl-compose

两条曲线只改 R 和 G，B（色相）原样往后传，所以 compose 拿到的色相还是原图的。

为什么不是「把 S 当 V」

HSL 与 HSV 的差别就卡在这一层：V = L + C/2，而 C = (1−|2L−1|)·S 里带着饱和度。把 HSL 的 L 直接当 HSV 的 V 写进「HSV 明度」混合模式，中亮度饱和色实测偏 25～64 码（S=1、L=0.5 时正好差 C/2 = 64 码）。本算子内部按上式计算，不近似。

转换由 babl 的 HSLA float 完成，与 GIMP 自己的 HSL 同一口径。

实测

  • dual → compose 恒等往返：32 位浮点 0.0002 码，8 位 ≤ 1 码。
  • 在完整插件里（含 Hue 层与混合模式），tools/check_hsl_split.py 28 项全过： 改 S 曲线后结果 HSL 的饱和度 = f(原 S)，明度与色相误差 0.0001 码。

注意

  • 输出 alpha 恒 1，理由同 lb:hsl-dual。
  • 输入超出 0…1 的值会被夹紧；NaN 折成 0。

只要这一个

Windows 模块 hsl-compose.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 hsl-compose.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。这里的每个模块都是独立的 GEGL 模块，只链接 GIMP 自带的 GEGL 与 babl，不依赖本项目里的其它模块——下这一个就够用，不会缺东西。要一次装齐，用整包。

HSL Compose

lb:hsl-compose Component area

Turns the HSL data image back into real colour. The mirror half of HSL Dual Extract — without it the packed channels mean nothing.

Menu: Colors → SuperMrWang → Component → HSL Compose (a filter op)

Overview

Restores a data image to real colour: R = saturation, G = lightness, B = hue/360 (all 0…1) go in, the matching HSL colour comes out, alpha is 1.

(R=S, G=L, B=H/360) ──lb:hsl-compose──> real colour

The input convention is strict

The operator cannot tell a data image from an ordinary photo — it always reads R as saturation, G as lightness and B as hue. Put it in the wrong place and it will happily turn a photo into nonsense.

The intended chain keeps it right behind lb:hsl-dual, with the curves in between:

lb:hsl-dual → S curve (red) → L curve (green) → lb:hsl-compose

The two curves only touch R and G, so B (hue) passes through untouched and compose sees the original hue.

Why not just treat S as V

The difference between HSL and HSV sits exactly here: V = L + C/2, and C = (1−|2L−1|)·S carries the saturation. Feeding HSL's L straight into the "HSV value" blend mode is off by 25–64 codes on mid-lightness saturated colours (at S=1, L=0.5 the error is exactly C/2 = 64 codes). This operator computes the formula above instead of approximating it.

The conversion is babl's HSLA float, the same one GIMP's own HSL uses.

Verification

  • dual → compose identity round trip: 0.0002 codes in 32-bit float, ≤ 1 code in 8-bit.
  • Inside the full plug-in (Hue layer and blend mode included), all 28 assertions in tools/check_hsl_split.py pass: after editing the S curve the result's HSL saturation equals f(original S), with lightness and hue within 0.0001 codes.

Notes

  • Output alpha is always 1, for the same reason as lb:hsl-dual.
  • Input outside 0…1 is clamped; NaN folds to 0.

Just this one

Windows module hsl-compose.dll, drop it into %LOCALAPPDATA%\gegl-0.4\plug-ins; Linux module hsl-compose.so, drop it into ~/.local/share/gegl-0.4/plug-ins, then restart GIMP. Every module here is a standalone GEGL module: it links only against the GEGL and babl that ship with GIMP, never against another module of this project, so one download is all it needs. The full bundle is on the download page.
