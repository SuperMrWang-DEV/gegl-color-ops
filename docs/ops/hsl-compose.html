HSL Compose

lb:hsl-compose 分量 整块区域

HSL 分量曲线工作流的合成器：把「R = 饱和度、G = 明度、B = 色相/360」的数据图还原成真实颜色

把数据图还原成真实颜色：R = 饱和度、G = 明度、B = 色相/360（都是 0…1）， 输出对应的 HSL 颜色，alpha 恒为 1。

(R=S, G=L, B=H/360) ──lb:hsl-compose──> 真实颜色

输入约定是硬的

本算子无法分辨输入是一张数据图还是一张普通照片——它一律按「R 是饱和度、G 是 明度、B 是色相」解释。挂错地方会把照片当成数据算出一张乱七八糟的图。

正常用法是紧跟在 lb:hsl-dual 之后（中间夹两条曲线）：

lb:hsl-dual → S 曲线(红) → L 曲线(绿) → lb:hsl-compose

两条曲线只改 R 和 G，B（色相）原样往后传，所以 compose 拿到的色相还是原图的。

为什么不是「把 S 当 V」

HSL 与 HSV 的差别就卡在这一层：V = L + C/2，而 C = (1−|2L−1|)·S 里带着饱和度。 把 HSL 的 L 直接当 HSV 的 V 写进「HSV 明度」混合模式，中亮度饱和色实测偏 25～64 码（S=1、L=0.5 时正好差 C/2 = 64 码）。本算子内部按上式计算，不近似。

转换由 babl 的 HSLA float 完成，与 GIMP 自己的 HSL 同一口径。

实测

  • dual → compose 恒等往返：32 位浮点 0.0002 码，8 位 ≤ 1 码。
  • 在完整插件里（含 Hue 层与混合模式），tools/check_hsl_split.py 28 项全过： 改 S 曲线后结果 HSL 的饱和度 = f(原 S)，明度与色相误差 0.0001 码。

注意

  • 输出 alpha 恒 1，理由同 lb:hsl-dual。
  • 输入超出 0…1 的值会被夹紧；NaN 折成 0。

只要这一个

Windows 模块 hsl-compose.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins，然后重启 GIMP。整包在 下载页。
