Lab Dual Extract

lb:lab-dual 分量 整块区域

Lab 分量曲线工作流的提取器：把一张图拆成「R = a、G = b、B = L」的数据图，一张图同时携带三个分量

把一张图打包成一张数据图：R = a*、G = b*、B = L*，全部 0…1。alpha 恒为 1。

原图 ──lb:lab-dual──> (R=a, G=b, B=L)
                          │
                    ┌─────┴─────┐
                 a 曲线(红)   b 曲线(绿)
                    └─────┬─────┘
                          ▼
                    lb:lab-compose  ──> 真实 Lab 颜色
                          │
                    （上面再叠一层 L 曲线，用 LCh 明度模式换 L*）

为什么 a 和 b 要挤进同一张图

Lab 的 a、b 是直角坐标，而 GIMP 的分量混合模式只认识 HSV / LCh / Luminance 这些——没有「a」也没有「b」。看起来 LCh 的 C（彩度）和 h（色相）是 a/b 的极坐标形式，似乎能借：

C = √(a² + b²)        h = atan2(b, a)

但每层的曲线只看得到自己那一个标量。要让 a 曲线和 b 曲线各自独立地映射，必须先把 (a, b) 两个值同时拿到手，再一起换算成 (C, h)；而「LCh 彩度」那一层手上只有一个 C，它没法知道 b 变成了多少。所以两条一维曲线拼不出这个二元映射——只能联合算：

a 曲线 ─┐
        ├─> (a', b') ─> Lab ─> 真实颜色
b 曲线 ─┘

这一层算出来的本来就是完整颜色（含 L∗），于是「L 层」只留一条 LCh 明度 模式： Lab 的 L∗ 和 LCh 的 L∗ 是同一个量，所以那一步是逐位精确的，不用任何近似。

输入输出

格式含义
inputR'G'B'A float滤镜栈的编码域缓冲，与 component-extract 同域
outputR'G'B'A float数值是数据不是颜色：0.745 / 0.502 / 0.382 = a∗ 62、b∗ 0、L∗ 38

量程按 babl 的 CIE Lab float（D50 白点，与 GIMP 的 Lab 空间同一口径）：

a' = (a* + 128) / 255      中性灰 a* = 0 落在 0.502
b' = (b* + 128) / 255      中性灰 b* = 0 落在 0.502
L' = L* / 100

alpha 恒写 1：分量层必须不透明，透明度交给组蒙版（半透明的混合层会按 alpha 做 lerp 而不是纯替换）。

实测

tools/check_lab_split.py 里 dual → compose 恒等往返：32 位浮点图 0.010 码， 8 位图 0.499 码（只剩量化）。改 a 曲线后，结果落在「a∗ 换了、b∗ 与 L∗ 都没动」的 Lab 点上，误差 0.0026 码（超过 0.5 码的像素 0 个）。

超 sRGB 色域的 Lab 点（a∗/b∗ 拉太猛时会出现）由 lb:lab-compose 按 [0,1] 裁掉——这是色域的事实，不是算子的误差。

注意

  • 输出是数据图，不要直接看它当照片：它看起来是某种奇怪的彩色，这是正常的。
  • 它和 lb:lab-compose 是配对使用的。只装一个没有意义。
  • 浮点图里负值/超 1 的值不会被砍掉（曲线仍能读到），到 8 位投影时才裁。

只要这一个

Windows 模块 lab-dual.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 lab-dual.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。这里的每个模块都是独立的 GEGL 模块，只链接 GIMP 自带的 GEGL 与 babl，不依赖本项目里的其它模块——下这一个就够用，不会缺东西。要一次装齐，用整包。

Lab Dual Extract

lb:lab-dual Component area

Packs a* and b* into two channels of one data image so two curves can move them independently — Lab's axes have no blend mode of their own in GIMP.

Menu: Colors → SuperMrWang → Component → Lab Dual Extract (a filter op)

Overview

Packs an image into one data image: R = a*, G = b*, B = L*, all 0…1. Alpha is always 1.

input ── lb:lab-dual ──> (R=a, G=b, B=L)
            │
            ├── a curve (red)
            ├── b curve (green)
            ▼
     lb:lab-compose ──> real Lab colour
            │
     (an L curve can then sit on top, LCh lightness mode)

Why a and b share one image

Lab's a and b are rectangular coordinates, and GIMP's component blend modes only know HSV / LCh / Luminance — there is no "a" and no "b". LCh's C (chroma) and h (hue) are the polar form of a/b, so it looks like they could stand in:

C = √(a² + b²)        h = atan2(b, a)

But each layer's curve only sees its own single scalar. For the a curve and the b curve to map independently, both values have to be in hand at the same time and converted to (C, h) together — while the "LCh chroma" layer holds only a C and cannot know what happened to b. Two 1D curves cannot express that two-variable map; it has to be computed jointly:

a curve ─┐
         ├─> (a', b') ─> Lab ─> real colour
b curve ─┘

What comes out is already a complete colour (L∗ included), so the "L layer" only needs one LCh lightness mode: Lab's L∗ and LCh's L∗ are the same quantity, which makes that step bit-exact with no approximation.

Input and output

FormatMeaning
inputR'G'B'A floatthe filter stack's encoding-domain buffer, same domain as component-extract
outputR'G'B'A floatthe numbers are data, not colour: 0.745 / 0.502 / 0.382 = a∗ 62, b∗ 0, L∗ 38

Ranges follow babl's CIE Lab float (D50 white point, the same Lab space GIMP uses):

a' = (a* + 128) / 255      neutral grey a* = 0 lands on 0.502
b' = (b* + 128) / 255      neutral grey b* = 0 lands on 0.502
L' = L* / 100

Alpha is written as 1 unconditionally: a component layer has to be opaque, and transparency belongs on a group mask — a semi-transparent blend layer would lerp with alpha instead of replacing.

Verification

tools/check_lab_split.py runs the dual → compose identity round trip: 0.010 codes on a 32-bit float image, 0.499 codes on 8-bit (quantisation only). After editing the a curve the result lands on the Lab point where "a∗ moved, b∗ and L∗ did not", within 0.0026 codes (zero pixels over 0.5 codes).

Lab points outside sRGB (which happens when a∗/b∗ are pushed hard) are clipped to [0,1] by lb:lab-compose — that is the gamut, not an error in the operator.

Notes

  • The output is a data image — do not read it as a photo. It looks like a strange colour image; that is expected.
  • It is only meaningful together with lb:lab-compose.
  • Negative or above-1 values are not truncated in float images (the curves can still read them); clipping happens when the result is projected to 8-bit.

Just this one

Windows module lab-dual.dll, drop it into %LOCALAPPDATA%\gegl-0.4\plug-ins; Linux module lab-dual.so, drop it into ~/.local/share/gegl-0.4/plug-ins, then restart GIMP. Every module here is a standalone GEGL module: it links only against the GEGL and babl that ship with GIMP, never against another module of this project, so one download is all it needs. The full bundle is on the download page.
