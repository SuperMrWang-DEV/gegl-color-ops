Color Lookup

lb:color-lookup 混合与通道 整块区域

按 .cube 3D LUT（可带 1D shaper）做颜色查找，等价于经典图像编辑器「颜色查找」调整图层；强度按 0..1 与原图线性混合

按 Adobe Cube LUT 规范实现的「颜色查找」，对应 经典图像编辑器的「颜色查找」调整图层。 经典图像编辑器 那侧只能手动跑脚本标定（见文末），所以这一支的数值验收先对齐独立写的 Python 参考实现，而不是 经典图像编辑器 输出。

  • GEGL id：lb:color-lookup
  • 菜单：Colors → SuperMrWang → Blend → Color Lookup
  • 类型：GeglOperationFilter（按行扫描；LUT 在 prepare() 里加载并缓存）
  • 参数：file（.cube 路径）、strength（0…1，默认 1）、 interpolation（trilinear 默认 / tetrahedral）

算法

  1. 解析：LUT_1D_SIZE / LUT_3D_SIZE / DOMAIN_MIN / DOMAIN_MAX / LUT_1D_INPUT_RANGE / LUT_3D_INPUT_RANGE / TITLE / # 注释。 节点值按声明的 domain 归一化到 0..1（DOMAIN_MAX 255 的表因此与 0..1 表等价）。
  2. 1D shaper（可选）：逐通道线性插值，先压一段曲线。
  3. 3D 表：文件里红变化最快，索引 r + g·n + b·n²。采样两种：
    • 三线性：8 个角点按体积权重相加；
    • 四面体：按 fr/fg/fb 的大小关系把立方体切成 6 个四面体，每个只走 3 条棱。 灰轴附近不会出现三线性的楔形偏色，但离格点越远、表越不平滑， 与三线性的差别越大（zigzag 表上可达 0.35，约 90 码）。
  4. 强度：out = 源 + (查表结果 − 源) · strength，在编码值上做 lerp。
  5. 输出夹到 0..1；alpha 原样透传。

格式支持：只认 .cube（3D、纯 1D、1D+3D 都行）。.3dl / .look / .csp 尚未实现 —— .3dl 的轴序（红最快还是蓝最快）需要拿 经典图像编辑器 实测确认，不能靠猜。

为什么钉在感知格式

LUT 是给编码值（0..1 的 sRGB 码）定义的。pad 固定成 R~G~B~A float， 喂线性光会把整张表往错误的位置上采样，暗部会明显发灰。

坏文件怎么办

解析失败（文件不存在、节点数不足、LUT_3D_SIZE 越界）时 g_warning 一条， 算子退化成恒等。渲染不中断，也不会因为一个坏路径把整张图弄黑。

缓存键是「路径 + mtime + size」，只在 prepare() 里 stat 一次， 同一路径被替换了文件也会自动重载。

性能

process() 每像素：3 次（1D）+ 8 次（3D）表访问 + 约 20 次乘加。 33³ 是常见尺寸（约 430 KB），对缓存友好；纯 1D 表只走 3 次插值。

验收

python tools/check_color_lookup.py            # 7 个内置 LUT × 2 种插值 × 3 档强度
python tools/check_color_lookup.py x.cube     # 额外比对指定文件

内置用例：2 格/33 格单位元、反相、R/B 对调、平滑非线性（DOMAIN 0..1 与 DOMAIN_MAX 255 各一份，结果须一致）、zigzag9（专门区分两种插值）、纯 1D 表。 与独立 Python 实现逐像素比对，全部 0.00 码（8 位下逐位相同）。

经典图像编辑器 侧待办

经典图像编辑器 2025 以「命令行带脚本」启动时，所有 Mk（建立调整图层）都会报 「命令建立: 当前不可用」——连亮度/对比度都建不出来，是启动期 UI 未就绪， 与描述符无关；executeAction(colorLookup) 当事件执行则不报错但不改像素。 所以要把 color-lookup-cal/batch_cl.jsx 存到本地、在已启动的 经典图像编辑器 里 文件 → 脚本 → 浏览… 手动跑一次，再用 color-lookup-cal/compare.py 对比 经典图像编辑器 输出与算子输出（脚本会同时报「经典图像编辑器 vs 三线性」「经典图像编辑器 vs 四面体」， 顺便定下 经典图像编辑器 到底用哪种插值）。

只要这一个

Windows 模块 color-lookup.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 color-lookup.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。整包在 下载页。

Color Lookup

lb:color-lookup Blend area

the classic editor's Color Lookup adjustment built on the Adobe Cube LUT spec — trilinear or tetrahedral interpolation, with strength.

An implementation of "Color Lookup" following the Adobe Cube LUT specification, matching the classic editor's Color Lookup adjustment layer. the classic editor can only be calibrated with a manually-run script here (see the end), so numeric acceptance targets an independently written Python reference rather than the classic editor output.

  • GEGL id: lb:color-lookup
  • Menu: Colors → SuperMrWang → Blend → Color Lookup
  • Type: GeglOperationFilter (row scan; the LUT is loaded and cached in prepare())
  • Parameters: file (a .cube path), strength (0…1, default 1), interpolation (trilinear default / tetrahedral)

Algorithm

  1. Parse: LUT_1D_SIZE / LUT_3D_SIZE / DOMAIN_MIN / DOMAIN_MAX / LUT_1D_INPUT_RANGE / LUT_3D_INPUT_RANGE / TITLE / # comments. Node values are normalised to 0..1 by the declared domain, so a table with DOMAIN_MAX 255 behaves the same as a 0..1 table.
  2. 1D shaper (optional): per-channel linear interpolation, one curve first.
  3. 3D table: red varies fastest in the file, index r + g·n + b·n². Two ways to sample:
    • trilinear: the 8 corners weighted by volume;
    • tetrahedral: split the cube into 6 tetrahedra according to the ordering of fr/fg/fb, each using only 3 edges. No trilinear wedge near the grey axis, but the further from a lattice point and the less smooth the table, the more it differs from trilinear (up to 0.35 on the zigzag table, about 90 code values).
  4. Strength: out = source + (lookup − source) · strength, lerped on encoded values.
  5. Output clipped to 0..1; alpha passes through untouched.

Format support: .cube only (3D, pure 1D, 1D+3D). .3dl / .look / .csp are not implemented — .3dl's axis order (red fastest or blue fastest) would need to be confirmed against the classic editor, and guessing is not good enough.

Why the perceptual format is pinned

A LUT is defined for encoded values (0..1 sRGB code). The pad is pinned to R~G~B~A float; feeding linear light samples the table at the wrong place and the shadows visibly turn grey.

Bad files

On a parse failure (missing file, too few nodes, LUT_3D_SIZE out of range) the operator emits one g_warning and degrades to identity. Rendering is not interrupted, and one bad path cannot turn the whole image black.

The cache key is "path + mtime + size", stat'ed once in prepare(), so replacing the file at the same path reloads it automatically.

Performance

Per pixel, process() does 3 (1D) + 8 (3D) table reads and about 20 multiply-adds. 33³ is the common size (about 430 KB) and cache-friendly; a pure 1D table needs only 3 interpolations.

Acceptance

python tools/check_color_lookup.py            # 7 built-in LUTs × 2 interpolations × 3 strengths
python tools/check_color_lookup.py x.cube     # additionally compare a given file

Built-in cases: 2-point and 33-point identity, invert, R/B swap, a smooth non-linearity (one with DOMAIN 0..1 and one with DOMAIN_MAX 255, which must agree), zigzag9 (specifically to separate the two interpolations) and a pure 1D table. Compared pixel by pixel against the independent Python implementation, all 0.00 code values (bit-identical at 8 bits).

the classic editor-side to-do

When the classic editor 2025 is launched with a script on the command line, every Mk (create adjustment layer) reports "command not currently available" — even brightness/contrast fails. The UI is simply not ready that early and it has nothing to do with the descriptor; running executeAction(colorLookup) as an event does not error but does not change pixels either. So save color-lookup-cal/batch_cl.jsx locally, run it by hand from an already-running the classic editor via File → Scripts → Browse…, then compare the classic editor output with the operator using color-lookup-cal/compare.py (the script reports both "the classic editor vs trilinear" and "the classic editor vs tetrahedral" and thereby settles which interpolation the classic editor uses).
