Maximum / Minimum

lb:max-min 蒙版 AreaFilter

形态学的两个基本算子，也是 Photoshop「最大值 / 最小值」滤镜的等价物：每个像素取邻域内最大（膨胀）或最小值（腐蚀）。最大值把亮区向外推、吞掉暗处的小点；最小值反过来收亮区、啃掉残留的白边。蒙版精修、去灰尘点、发光底图都用它。

两个方向、四个参数、一份在缓冲自身精度里跑的滑动极值。下面从「GIMP 为什么已经没有它」讲起，再讲算法、精度、边界，最后是验证方法与实现里踩过的两个坑。

        ┌─────────────┐               ┌─────────────┐
输入 ──▶│ 取邻域最大值 │──▶ 亮区外扩   │ 取邻域最小值 │──▶ 亮区收缩
        └─────────────┘               └─────────────┘

最大值把亮区往外推、吞掉暗处的小点；最小值反过来收亮区、啃掉抠图残留的白边。蒙版精修、去灰尘点、发光底图、做描边都用它。

GIMP 里为什么得自己写

GIMP 2.10 之前有「滤镜 → 通用 → 膨胀 / 腐蚀」，之后交给 GEGL 的 gegl:dilate / gegl:erode。这两个属于 GEGL 的 workshop 算子，官方 Windows 构建没有把它们编进来：

$ gegl --list-all | grep -E "dilate|erode"      # 空
$ 查 PDB plug-in-dilate                          # None
$ strings libgegl-0.4-0.dll | grep gegl:dilate   # 空

本机 GIMP 3.2.8 上确认三条都为空。剩下的只有 gimp-selection-grow / -shrink，但它们只作用于选区，改不了一张蒙版或一个图层的像素。

所以这个算子不转调任何原生过程，是自己算的——这也是本项目里为数不多的「不能拿原生当基准」的算子，好在形态学的定义是完全确定的，见下面的验证。

参数

参数范围说明
modemaximum / minimum最大值（膨胀）/ 最小值（腐蚀）
radius1–100邻域半径像素。r=1 即 3×3，边缘向外长一圈
shapesquare / round方窗 (±r, ±r)；圆盘 r。对应 PS 的方形度 / 圆度
affect-alpha布尔，默认关关掉时 alpha 原样透传（PS 同样不动图层透明度）

半径语义与 Photoshop 一致：r 表示检查 (±r, ±r) 的邻域，不是窗口边长。所以 r=1 得到的正是 3×3，而不是 2×2。

圆盘结构元用 dx² + dy² ≤ r² 判定，等价于逐行取半宽 ⌊√(r²−dy²)⌋：

rdy=0dy=±1dy=±2dy=±3
110——
2210—
33220

算法

方窗可分离：二维方窗的极值 = 先横向取一次、再纵向取一次，两遍都是一维滑动极值。一维用 van Herk / Gil-Werman：按窗口宽度分块，块内先算前缀与后缀极值，任意一个窗口恰好被「起始处的后缀 + 末端处的前缀」拼满，每像素两次比较。总复杂度 O(n)，与半径无关。

圆盘不可分离（每行半宽不同），退化为逐 dy 做横向极值、再纵向累积， O(n·r)。半径 100 时的比较次数约为方窗的 100 倍，但极值只有比较没有乘法， 3MP 图仍在秒级。

实测（3.0 MP，u8 RGB，单线程）：

形状半径耗时
方窗113 ms
方窗10043 ms
圆盘1063 ms
圆盘1001.26 s

方窗 r=1 与 r=100 只差 3 倍，正好印证复杂度与半径无关。

精度：三个类型各展开一份

极值只需要大小关系，但结果值必须原样搬出来。所以 maxmin-kernel.h 是一份模板头文件，被 max-min.c 以不同的 PLANE_T 宏包含三次，生成 u8 / u16 / float32 三份同构代码：

#define PLANE_T     guint8
#define PLANE_BAND  band_u8
#include "maxmin-kernel.h"

缓冲是什么精度就在什么精度里比较，中途不做任何格式转换。把 u16 读成 float 再写回，个别像素会差 1 码——这里不给它机会。同理不做色彩管理、不做 gamma 换算： PS 的这两个滤镜也是直接对通道值取极值，跟着它的语义走，彩色图上才会得到一样的偏色。

边界

画布外按复制边缘像素处理。对取极值而言，这与「只算窗口内的那部分」逐位等价：补进来的永远是边缘那一列 / 那一行的副本，而那一列本来就在窗口里，不引入任何新值。所以不像模糊那样会在边缘暗一圈，也不需要额外的边界策略参数。

逐通道

三个色 / 灰度分量各自独立取极值，alpha 默认不参与。这是 PS 的语义：滤镜不改图层透明度。要连 alpha 一起算，把 affect-alpha 打开。

彩色图上因此会出现偏色（红蓝交界处冒紫边），这不是 bug，是逐通道运算的必然结果。要没有偏色就换成单色目标：蒙版、通道、灰度层。

正确性验证

本机没有可对照的原生实现，所以基准写成 O(r²) 的四重循环（tools/check_max_min.py 里的纯 Python brute()）——和 van Herk 是两条完全独立的代码路径：

python  tools/check_max_min.py   # 在 GIMP 的 python-fu 里跑，见文件头

27 项，覆盖：

  • u8 / u16 / float32 三种缓冲精度，逐字节 / 逐位相同
  • 方形与圆形 × 最大值与最小值 × 半径 1 / 2 / 5
  • 单通道 Y u8（蒙版的主战场）与 RGBA
  • alpha 默认不动 / affect-alpha 开
  • 图边缘（暴力实现同样钳位，两者必须一致）
  • 高 301 px 的图跨过 128 行的分带边界，验证拼接无接缝
  • 半径 100 在 9×7 的小图上（窗口比图还大）
  • 先最小后最大 = 开运算：孤立亮点被抹掉、方块保形
  • 2000×1500 的性能抽样

插件层另有 tools/check_max_min_plugin.py（12 项）：过程注册、非破坏滤镜挂载、蒙版走写像素、图层组拒绝、半径越界被参数校验挡住。

分带实现的一个坑

输入按 128 行一带读，横向余量 r 列、纵向余量 r 行，四个通道在同一带里一起算完才写回。通道循环必须在分带循环内部：反过来写，后一个通道会用输入重建整带，把前一个通道的结果覆盖回去——第一版就是这么错的，六项 u8 用例全挂，单通道（只有一路）反而全过，很容易看漏。

另一处：列方向的暂存区容量要按 max(pw, ph) 算。只按宽度 pw 分配，在「高瘦」的分带上会越界写（已踩过一次，表现为跑完若干用例后进程崩掉）。

只要这一个

Windows 模块 max-min.dll，放进 %LOCALAPPDATA%\gegl-0.4\plug-ins；Linux 模块 max-min.so，放进 ~/.local/share/gegl-0.4/plug-ins，然后重启 GIMP。这里的每个模块都是独立的 GEGL 模块，只链接 GIMP 自带的 GEGL 与 babl，不依赖本项目里的其它模块——下这一个就够用，不会缺东西。要一次装齐，用整包。

Maximum / Minimum

lb:max-min Mask AreaFilter

Morphological dilate and erode — Photoshop's Maximum / Minimum filter. Grows or shrinks bright areas, radius 1–100, square or disc, compared in the buffer's own precision.

The two basic morphological operators, and the equivalent of Photoshop's Maximum / Minimum filter: every output pixel takes the largest value in its neighbourhood (dilate) or the smallest (erode).

        ┌─────────────┐               ┌─────────────┐
in ────▶│ take max    │──▶ bright out │ take min    │──▶ bright in
        └─────────────┘               └─────────────┘

Maximum pushes bright areas outwards and swallows small dark specks; minimum shrinks bright areas and chews away the fringe left after a cut-out. Mask refinement, despeckling, glow bases and outlines all use it.

Why it has to be written here

Up to 2.10 GIMP had Filters → Generic → Dilate / Erode; afterwards GEGL's gegl:dilate / gegl:erode took over. Those are workshop operators and are not compiled into the official Windows build:

$ gegl --list-all | grep -E "dilate|erode"      # empty
$ PDB lookup plug-in-dilate                     # None
$ strings libgegl-0.4-0.dll | grep gegl:dilate  # empty

All three are empty on the 3.2.8 install this was written against. The only native leftovers are gimp-selection-grow / -shrink, and those act on selections only — they cannot change a mask or a layer's pixels.

So this operator calls no native procedure; it computes the result itself. That makes it one of the few here that cannot be validated against a native reference — but morphology is completely determined, see the verification section.

Parameters

ParameterRangeMeaning
modemaximum / minimumdilate / erode
radius1–100neighbourhood radius in pixels; r=1 is 3×3, one ring outwards
shapesquare / roundsquare window (±r, ±r); disc of radius r — PS's Squareness / Roundness
affect-alphaboolean, offwhen off, alpha is passed through (PS leaves layer opacity alone too)

Radius means the same as in Photoshop: it checks a (±r, ±r) neighbourhood, not a window edge length, so r=1 gives exactly 3×3 and not 2×2.

A disc uses dx² + dy² ≤ r², i.e. a per-row half-width of ⌊√(r²−dy²)⌋:

rdy=0dy=±1dy=±2dy=±3
110——
2210—
33220

Algorithm

A square window is separable: a 2D window extremum equals a horizontal pass followed by a vertical one, both 1D sliding extrema. The 1D pass uses van Herk / Gil-Werman: split the row into blocks the size of the window, compute prefix and suffix extrema inside each block, and any window is exactly covered by "the suffix starting at its left edge + the prefix ending at its right edge" — two comparisons per pixel. Total cost O(n), independent of the radius.

A disc is not separable (each row has a different half-width), so it falls back to one horizontal pass per dy accumulated vertically: O(n·r). At radius 100 that is about 100× the comparisons of a square window, but extrema are compares, not multiplies, so a 3 MP image is still seconds.

Measured on 3.0 MP u8 RGB, single thread:

ShapeRadiusTime
square113 ms
square10043 ms
disc1063 ms
disc1001.26 s

Square r=1 versus r=100 differing by only 3× is the O(n) claim in practice.

Precision: three copies of the kernel

An extremum only needs ordering, but the value itself must be carried out untouched. So maxmin-kernel.h is a template included three times by max-min.c with different PLANE_T macros, generating identical u8 / u16 / float32 code:

#define PLANE_T     guint8
#define PLANE_BAND  band_u8
#include "maxmin-kernel.h"

The buffer's own precision is the precision used for the comparison, with no format conversion in between. Reading a u16 as float and writing it back moves individual pixels by one code — that is not allowed here. Equally, no colour management and no gamma conversion: PS's Maximum / Minimum also work straight on channel values, and following that semantics is what reproduces the same colour fringing.

Borders

Outside the canvas the edge pixels are replicated. For an extremum that is bit-identical to only counting the in-canvas part of the window: the replicated values are copies of an edge pixel that is already inside the window, so no new value enters. Unlike a blur, nothing darkens at the border — and no extra abyss parameter is needed.

Per channel

Each colour / grey component is processed independently and alpha is left alone by default, which is PS's semantics too: the filter does not change layer opacity. Turn affect-alpha on to include it.

Colour images therefore show fringing (magenta along red/blue edges). That is not a bug, it is what per-channel extrema do. To avoid it, target a single-plane drawable: a mask, a channel or a greyscale layer.

Verification

There is no native implementation on this machine to compare against, so the reference is an O(r²) four-deep loop (the plain-Python brute() in tools/check_max_min.py) — a completely separate code path from van Herk:

python  tools/check_max_min.py   # runs inside GIMP's python-fu, see the header

27 checks covering:

  • u8 / u16 / float32, byte-for-byte / bit-for-bit identical
  • square and disc × maximum and minimum × radii 1 / 2 / 5
  • single-channel Y u8 (the mask case) and RGBA
  • alpha untouched by default, and with affect-alpha on
  • image borders (the brute force clamps too, so both must agree)
  • a 301 px tall image crossing the 128-row band boundary, to prove the bands join
  • radius 100 on a 9×7 image, where the window is larger than the canvas
  • minimum then maximum (an opening): the isolated speck disappears, the square holds
  • a 2000×1500 performance sample

The plug-in layer has its own tools/check_max_min_plugin.py (12 checks): procedure registration, non-destructive filter attachment, mask baking, layer-group rejection, out-of-range radius stopped by the argument check.

Two traps in the banded implementation

Input is read in 128-row bands with r pixels of horizontal and vertical margin, all channels processed before the band is written back. The channel loop must sit inside the band loop: the other way round, the next channel rebuilds the band from the input and overwrites the previous channel's result. That was the first version — six u8 cases failed while the single-channel ones all passed, which makes it easy to miss.

And the column scratch buffer must be sized max(pw, ph). Allocating only pw bytes writes out of bounds on tall, narrow bands — which shows up as the plug-in crashing after a dozen cases rather than as a wrong pixel.

Just this one

Windows module max-min.dll, drop it into %LOCALAPPDATA%\gegl-0.4\plug-ins; Linux module max-min.so, drop it into ~/.local/share/gegl-0.4/plug-ins, then restart GIMP. Every module here is a standalone GEGL module: it links only against the GEGL and babl that ship with GIMP, never against another module of this project, so one download is all it needs.
