安装与排错

没有安装程序，也没有注册表：把模块文件放进 GEGL 的插件目录，重启 GIMP 就完事。

环境要求

  • GIMP 3.x（3.0 / 3.2 实测），自带 GEGL 0.4。
  • Windows x64 用现成的 .dll，Linux x86_64 用 .so。 Windows 包 50 个模块齐全；Linux 包目前 47 个，component 家族那 3 个模块（hsv / hsl / lab / lch / hsi 各自的 dual 与 compose，再加 gray-to-component）还没出包，可以 ./build.sh 自己编。
  • 不需要 Python 运行时——算子是 C 编译的 GEGL 模块。

安装

把压缩包解开，把里面的模块文件（.dll / .so）全部放进 用户插件目录（目录不存在就新建）：

系统目录
Windows%LOCALAPPDATA%\gegl-0.4\plug-ins
Linux~/.local/share/gegl-0.4/plug-ins
macOS~/Library/Application Support/gegl-0.4/plug-ins

然后完全退出 GIMP 再打开（不是关窗口）。模块只在启动时扫描一次。

确认加载成功，可以在命令行问 GEGL：

gegl --info lb:hsl-levels

能打印出参数表就说明注册上了。GIMP 自带的 gegl 在安装目录的 bin/ 里，Windows 上通常是 C:\Program Files\GIMP 3\bin\gegl.exe。

别忘了包里那个 locale 目录

下载包里除了模块，还有 locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo—— 那就是中文语言包。解压时连目录一起放进 gegl-0.4/plug-ins， 最终是 plug-ins/locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo。 漏了它不会报错：算子照常工作，只是菜单名和参数说明回落到英文。

Python 插件包同理：GIMP 的插件目录里除了 .py，还要有 _shared/（翻译取值 lb_i18n.py + 参数对话框 lb_dialog.py）和 locale/（语言包）， 即 plug-ins/_shared/ 与 plug-ins/locale/。 少了 lb_dialog.py 不会报错，但点菜单会直接用默认值跑、 不弹参数框。

只有 AI 局部重绘还要额外一样东西：本机的 ComfyUI。它的下载包里带 ai-setup/，双击一次 setup-ai.bat 就把 ComfyUI、torch 和一份底模装好（约 10 GB，无人值守）；之后在 SuperMrWang → AI → AI Environment… 里点 Start ComfyUI。其余插件不需要它。

界面语言

翻译跟着 GIMP 的界面语言走，不跟操作系统走：

  • GIMP 3：编辑 → 首选项 → 界面 → 语言，选「中文（简体）」，完全退出再打开。
  • 命令行验证：LANG=en_US.UTF-8 gimp 出英文、LANG=zh_CN.UTF-8 gimp 出中文（Linux / macOS）；Windows 可以先 set LANGUAGE=zh_CN 再启动 GIMP。
  • 只想单独试一份语言包：LB_LOCALEDIR=/path/to/locale gimp。

切完语言菜单名可能还停在旧语言：GIMP 把插件的菜单名缓存进 pluginrc， 里面存的是已经翻译好的字符串，不带语言标记，所以切语言它不会自己失效。 关掉 GIMP，删掉 %APPDATA%\GIMP\3.x\pluginrc （Linux 是 ~/.config/GIMP/3.x/pluginrc）再启动即可。 算子那边不受影响——它们每次启动都重新取。

怎么用

菜单栏顶层多了 SuperMrWang（和「颜色」「图层」平级），算子按 Levels（色阶家族）/ Component（dual + compose 与 gray-to-component）/ Tone / Color / Blend / Mask 归组；Python 插件另占 Convert（图层 → 选区 / 通道 / 拆分量）、Mask（Alpha Curves、Color Range）、 Blend（应用图像、计算）、Retouch（五个分量曲线 + 三个磨皮）。 图层右键菜单用同一套 Convert / Mask / Retouch，只列对单层能用的。 也可以在 /（搜索动作）里直接输算子名。

绝大多数算子是 Point 或 Filter 类型，GIMP 会把它们当非破坏性 fx 挂在图层上——参数随时能改，原像素不动。双输入算子（应用图像 / 计算）目前只能合并应用。

自己编（可选）

需要 GIMP 3 自带的 GEGL 开发头文件与 gcc（Windows 上 MSYS2 的 mingw64 工具链即可）：

git clone https://github.com/SuperMrWang-DEV/gegl-color-ops.git
cd gegl-color-ops
./build.sh              # 产物在 build/
./install.sh --verify   # 顺带拷进插件目录并逐个验证注册

Linux / macOS 也可以用 meson：

export PKG_CONFIG_PATH="/path/to/gimp/lib/pkgconfig"
meson setup build-meson && ninja -C build-meson

排错

菜单里看不到

  • 路径对不对：必须是 gegl-0.4/plug-ins，不是 GIMP 的 plug-ins。
  • 有没有重启：GIMP 启动后才扫描，热拷进去不生效。
  • 只看到一部分算子：先数模块数——整包是 47 个。旧包只装 43 个， 新加的锐化 / 杂色 / 置换就不在菜单里。重装一次整包，或源码目录里跑 ./install.sh --no-build --verify（装 build/ 里现成的产物， 再用 gegl --info 逐个确认注册）。
  • 位数/依赖：用 GIMP 自带的那份 GEGL 运行时，别混用系统里另一套 GEGL。
  • 用 gegl --info lb:xxx 单独验：命令行能看到、GIMP 看不到，通常是 GIMP 版本太旧。

同一个算子出现两次 / 报重复注册

插件目录里同时存在旧文件名的模块（早期是 12 个独立仓库，文件名不一样）。 删掉旧名字的 .dll 即可，详见仓库 README.md 的「与旧布局的对应关系」。

打开旧图提示未知参数

算子升级时偶尔会删掉合并过的参数，旧 XCF 里存的值会丢。加载只警告、不报错， 但要重新调一次。升级前建议先另存一份。

菜单和参数说明是英文的

  • 语言包没放对：确认 plug-ins/locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo 在（算子和插件共用这一份）。
  • GIMP 界面语言不是中文：翻译跟界面语言走，不是跟系统语言，见上面「界面语言」。
  • 插件菜单名没刷新：删掉 pluginrc 再启动，那里缓存了上一次的语言。

精度里的「码」是什么

算子页和插件页里到处写着「恒等往返 0.0002 码」「残差 0.30 码」——1 码就是 8 位 图上的一个台阶：0–255 共 256 级，相邻两级之间的差就是 1 码，等于 1/255 ≈ 0.392%。所以「0.0002 码」的意思是：结果的编码值比原图最多差 0.0002 个台阶，也就是 RGB 128 变成 128.0002。

为什么用这把尺子：浮点误差本身没有直观意义（1e-7 是好是坏取决于位深和做过多少次 运算），换成「折算成 8 位输出会差几级」之后，所有空间、所有位深都可以横向比， 而且直接对上肉眼的分辨极限。

数值意味着什么
0.0002 码1 码的 1/5000，浮点上的一次干净往返
0.0053 码1 码的 1/190，多层编码累积后的量级，仍不可见
0.49 码8 位量化本身的下限——任何一次输出 8 位图都躲不掉
1 码肉眼几乎不可见，并排才勉强看出
3–4 码开始能看出差异，渐变面上可能看到色带边界
8 码以上明显偏色或偏亮

它衡量的是「输出会不会变」，不是「人眼觉不觉得变」。这里取的是 sRGB 编码值 （R′G′B′）的最大绝对差——最坏的那个像素、最坏的那个通道，不是平均值。编码空间 不是感知均匀的：暗部的 1 码比亮部的 1 码更扎眼，要讨论「看起来差多少」得换到 Lab 里算 ΔE。所以同一份结果，码数是工程判据，ΔE 才是观感判据。

顺带一提：小于 0.5 码的差异在 8 位图上落不到不同像素上去（四舍五入会抹平它）， 只会在浮点工程图、或者连续叠加几十次同类运算时慢慢显形。这就是为什么插件页里 会同时给「32 位浮点」和「8 位」两组数字。

曲线为什么全是「平滑」，而且不吃精度

插件里给你调的那几条曲线，一律是 GIMP 的 SMOOTH（平滑样条），控制点 只有三到五个：(0,0) (128,128) (255,255) 这样的对角三点，或者 提亮/压暗曲线的五个点。另一种写法 FREE「手绘」看着更自由，其实是把 256 个采样点一个个塞进去：打开属性面板是一串密密麻麻的点，想动某一段得先在 一堆点里找准是哪一个，手一拖整条线就歪。三个抓手没有这个问题。

早先我以为「平滑必然要付精度代价」，实测下来这个结论是错的。关键在于控制点 落在哪：曲线内部只认 0…255 的整数档，x 也一样。写 0.5 表示 127.5/255，正好卡在两档中间，GIMP 会把它挪到某一侧， 于是这条「对角直线」并不真的过对角——恒等状态下差半码，8 位图上还会把相邻两档 并成一级（256 级只剩 217 级）。改成 128/255（踩在格点上）之后， 恒等往返实测 0.0002 码、256 级一级不少，与铺满采样点的老写法完全一致。 控制点仍然只有三个，照样拖得动。

顺带解答一个常见的想法：先铺 256 个采样点、再在面板里点「平滑」行不行？ 行，结果也是 0 误差——因为 GIMP 转换时把控制点放在了 32/255 的 格点上，等于它替你踩了格子。但它把 256 个点重新拟合成 9 个控制点，原来的 采样表被丢掉，而且这一步不可逆：手绘时留的硬拐角会被磨圆，想找回原样只能重画。 我们直接生成踩格点的三个点，省掉这一步，也不丢任何东西。

两类曲线分得很清：给人调的走平滑样条；机器自己用的编码表（比如把 L* 0–100 铺满灰阶、把色相 0–360° 缩进 0–255）仍然是采样点——它的形状是算 出来的，不是画出来的，也不需要抓手。

实测对照（同一张图、同样的恒等曲线，旧写法 FREE 256 点 vs 现写法 SMOOTH 三点）：

插件FREE 256 点SMOOTH 三点（踩格点）8 位
HSV0.00015 码0.00015 码0.49 码
HSL0.00012 码0.00012 码0.49 码
Lab0.00243 码0.00243 码0.49 码
LCh0.00049 码0.00049 码0.49 码
HSI0.00014 码0.00014 码0.50 码

两列数字一模一样。8 位的 0.49 码是量化本身，跟曲线无关。

常见问题

和经典图像编辑器的调整图层结果一致吗？

多数算子的目标是「肉眼与 8 位输出一致」。实测残差写在每篇算法说明里， 通常是中位 0–4 码；有明确对不上的段落时也会说明（例如 经典图像编辑器 在个别对角线上的硬裁切）。

为什么叫 lb: 前缀？

GEGL 的 id 必须唯一。前缀避免和 GIMP 自带算子撞名——撞了会静默加载失败， 所以这个工程里所有 id 和 GType 名都带前缀。

会进 GIMP 官方仓库吗？

不会。这是独立的第三方算子集，按 GPL-3.0 发布，自己装进用户插件目录即可。

Install & troubleshooting

No installer, no registry: drop the module files into GEGL's plug-in directory and restart GIMP. That is the whole procedure.

Requirements

  • GIMP 3.x (tested on 3.0 and 3.2), which ships GEGL 0.4.
  • Prebuilt .dll for Windows x64, .so for Linux x86_64. The Windows bundle has all 50 modules; the Linux bundle currently has 47 — the 3 modules of the component family (dual and compose for hsv / hsl / lab / lch / hsi, plus gray-to-component) are not in the bundle yet — build them with ./build.sh.
  • No Python runtime needed: the operators are GEGL modules compiled from C.

Installing

Unpack the archive and copy every module file (.dll / .so) into the user plug-in directory (create it if it does not exist):

SystemDirectory
Windows%LOCALAPPDATA%\gegl-0.4\plug-ins
Linux~/.local/share/gegl-0.4/plug-ins
macOS~/Library/Application Support/gegl-0.4/plug-ins

Then quit GIMP completely and start it again (closing the window is not enough). Directories are scanned once, at startup.

To confirm the modules loaded, ask GEGL from a terminal:

gegl --info lb:hsl-levels

If it prints the property list, the operator is registered. GIMP's own gegl lives in the bin/ folder of its install directory — on Windows usually C:\Program Files\GIMP 3\bin\gegl.exe.

Do not leave the locale folder behind

Besides the modules, the archive contains locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo — the Chinese catalogue. Keep the directory when unpacking, so it ends up as plug-ins/locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo. Nothing breaks if you drop it: the operators still work, the menu names and parameter blurbs just fall back to English.

Same for the Python plug-in archives: next to the .py files GIMP's plug-in folder needs _shared/ (the translation lookup lb_i18n.py plus the dialog helper lb_dialog.py) and locale/ (the catalogue), i.e. plug-ins/_shared/ and plug-ins/locale/. Without lb_dialog.py nothing errors out, but the menu entry runs with defaults and never shows its parameter dialog.

Only AI Inpaint needs one more thing: a local ComfyUI. Its zip carries an ai-setup/ folder — run setup-ai.bat once and it installs ComfyUI, torch and one checkpoint (~10 GB, unattended); afterwards press Start ComfyUI in SuperMrWang → AI → AI Environment…. No other plug-in needs it.

Interface language

The translation follows GIMP's interface language, not the operating system:

  • GIMP 3: Edit → Preferences → Interface → Language, pick Chinese (Simplified), quit completely and start again.
  • From a terminal: LANG=en_US.UTF-8 gimp gives English and LANG=zh_CN.UTF-8 gimp Chinese (Linux / macOS). On Windows run set LANGUAGE=zh_CN before starting GIMP.
  • To point at one specific catalogue directory: LB_LOCALEDIR=/path/to/locale gimp.

Menu labels may stay in the old language after switching: GIMP caches plug-in menu names in pluginrc as already-translated strings with no language tag, so a language change does not invalidate them. Quit GIMP, delete %APPDATA%\GIMP\3.x\pluginrc (Linux: ~/.config/GIMP/3.x/pluginrc) and start it again. Operators are not affected — they resolve their strings on every start.

Using it

A top-level SuperMrWang menu appears next to Colors and Layers. Operators are grouped as Levels (the levels family), Component (dual + compose plus gray-to-component), Tone, Color, Blend and Mask; the Python plug-ins take Convert (layer → selection / channel, or one split into R/G/B/A), Mask (Alpha Curves, Color Range), Blend (Apply Image, Calculations) and Retouch (five component curves plus three retouching tools). The layer context menu uses the same Convert / Mask / Retouch split and only lists what works on a single layer. You can also type an operator name into the action search (/).

Almost every operator is a Point or Filter op, so GIMP attaches it to the layer as a non-destructive fx — parameters stay editable and the pixels are not touched. The two-input operators (Apply Image and Calculations) can only be applied destructively for now.

You need GIMP 3's GEGL development headers and gcc (MSYS2's mingw64 toolchain is enough on Windows):

Troubleshooting

Nothing shows up in the menu

  • Check the path: it must be gegl-0.4/plug-ins, not GIMP's own plug-ins.
  • Did you restart? The scan happens at startup, so copying files in while GIMP runs does nothing.
  • Architecture and dependencies: use the GEGL runtime that ships with GIMP, not a second GEGL from the system.
  • Verify with gegl --info lb:xxx: visible on the command line but missing inside GIMP usually means the GIMP version is too old.

The same operator appears twice / duplicate registration errors

An old module with a different file name is still in the plug-in directory (early on these were 12 separate repositories with unrelated names). Delete the old .dll; the mapping is listed in the repository's README.md under "relationship to the old layout".

Opening an old image warns about unknown properties

Upgrades occasionally remove properties that were merged into others, and the values stored in old XCFs are then dropped. Loading only warns, never fails, but you have to set those parameters again. Save a copy before upgrading.

Menus and parameter blurbs are in English

  • The catalogue is not where it should be: check that plug-ins/locale/zh_CN/LC_MESSAGES/gegl-color-ops.mo exists (operators and plug-ins share that one file).
  • GIMP's interface language is not Chinese: the translation follows the interface language, not the system locale — see "Interface language" above.
  • Plug-in menu labels were not refreshed: delete pluginrc and start GIMP again, it still holds the previous language.

What a "code" is

The operator and plug-in pages keep quoting figures like "identity round trip 0.0002 codes" or "residual 0.30 codes". One code is one step on an 8-bit image: 0–255 is 256 levels, so the gap between neighbours is 1 code, or 1/255 ≈ 0.392%. "0.0002 codes" therefore means the encoded result differs from the source by at most 0.0002 of a step — RGB 128 comes back as 128.0002.

Why that yardstick: floating-point error on its own says nothing (whether 1e-7 is good depends on bit depth and how many operations ran). Expressed as "how many 8-bit levels would this change", every colour space and bit depth becomes comparable, and the number lines up with what the eye can resolve.

ValueWhat it means
0.0002 codes1/5000 of a step — a clean float round trip
0.0053 codes1/190 of a step — the scale after several encode passes, still invisible
0.49 codesthe floor set by 8-bit quantisation; no 8-bit output escapes it
1 codebarely visible, and only side by side
3–4 codesvisible; banding may show on gradients
8 codes and upan obvious colour or brightness shift

It measures whether the output changed, not whether an eye would notice. The figure is the maximum absolute difference in sRGB encoded values (R′G′B′) — the worst pixel, the worst channel, never an average. The encoding space is not perceptually uniform: one code in the shadows is more visible than one code in the highlights, so "how different does it look" has to be computed as ΔE in Lab. Codes are the engineering criterion; ΔE is the perceptual one.

Worth adding: a difference below 0.5 codes cannot land on a different pixel in an 8-bit image (rounding swallows it). It only shows up in float working images, or after stacking dozens of similar operations. That is why the plug-in pages quote both a 32-bit float and an 8-bit number.

Why the curves are all SMOOTH, and why that costs no precision

Every curve handed to you in the plug-ins is GIMP's SMOOTH spline with three to five control points: a diagonal of (0,0) (128,128) (255,255), or the five points of a dodge/burn curve. The other form, FREE "hand-drawn", looks more flexible but is really 256 sample points pushed in one at a time: the property panel becomes a wall of dots, editing one segment means finding the right dot first, and one slip drags the whole line. Three handles do not have that problem.

I used to assume "smoothing must cost precision". Measured, that is wrong. What matters is where the control points sit: the curve only knows integer levels 0…255, and so does x. Writing 0.5 means 127.5/255, exactly between two levels; GIMP nudges it to one side, so the "diagonal" does not actually pass through the diagonal — the identity is half a code off, and in 8-bit two adjacent levels collapse into one (256 levels become 217). Put the point on 128/255 (on the grid) and the identity round trip measures 0.0002 codes with all 256 levels intact — identical to the old fully-sampled form, with three handles instead of 256 dots.

And a common idea: lay down 256 sample points, then hit "smooth" in the panel? That works too, also with zero error — GIMP places the converted control points on the 32/255 grid for you. But it refits those 256 points into 9 control points and throws the original table away, irreversibly: hard corners you drew get rounded, and the only way back is to redraw. Generating the three on-grid points directly skips that step and loses nothing.

The two kinds of curve are kept strictly apart: anything a person drags is a smooth spline; the encoding tables the machine uses for itself (L* 0–100 across the greyscale, hue 0–360° squeezed into 0–255) stay sampled — their shape is computed, not drawn, and they need no handles.

Measured side by side (same image, same identity curve, old FREE 256 points vs the current SMOOTH three points):

Plug-inFREE, 256 pointsSMOOTH, 3 points on grid8-bit
HSV0.00015 codes0.00015 codes0.49 codes
HSL0.00012 codes0.00012 codes0.49 codes
Lab0.00243 codes0.00243 codes0.49 codes
LCh0.00049 codes0.00049 codes0.49 codes
HSI0.00014 codes0.00014 codes0.50 codes

The two columns are identical. The 0.49 codes in the 8-bit column is quantisation itself, unrelated to the curve.

FAQ

Do the results match the classic editor's adjustment layers?

Most operators aim for "the same 8-bit output, to the eye". The measured residual is quoted in every algorithm page, usually 0–4 codes at the median; where something genuinely differs, the page says so (for example the classic editor's hard clipping on a few diagonals).

Why the lb: prefix?

GEGL ids have to be unique. The prefix avoids colliding with GIMP's own operators — a collision fails silently at load time — so every id and GType name in this project carries it.

Will this go into GIMP's official repository?

No. It is an independent third-party operator set, released under GPL-3.0, installed into your own user plug-in directory.
