# lb:ps-hue-saturation · Hue/Saturation (Basic)

三滑杆版本：全局色相旋转、饱和度相对缩放、明度向白/黑混合。不含「着色」复选框，
也没有分色相区间。行为上与常见图像软件的「色相/饱和度」对话框三根滑杆一致。

- GEGL id：`lb:ps-hue-saturation`
- 菜单：`Colors → SuperMrWang → Color → Hue/Saturation (Basic)`
- 类型：`GeglOperationPointFilter`（逐像素，无邻域）
- 参数：`hue`（−180…180°）、`saturation`（−100…100）、`lightness`（−100…100）

## 算法

在 **sRGB 编码值**（`R~G~B~A float`，感知域而非线性光）上，四步：

```
t = lightness / 100
r,g,b ← c + t·(1−c)   (t > 0)      # 与中性灰做滤色
        c·(1+t)       (t < 0)      # 与中性灰做正片叠底
h,s,l ← RGB2HSL(r,g,b)
h ← (h + hue) mod 360
x = saturation / 100
s ← s/(1−x)  (x > 0)                # 双曲放大
    s·(1+x)  (x < 0)                # 线性收缩
s ← clamp(s, 0, 1)
out = HSL2RGB(h, s, l)
```

顺序有意义：明度先落进 RGB，再把结果转 HSL 做色相与饱和度 —— 所以饱和度作用在
「提亮/压暗之后」的 S 上，而不是原图的 S。

## 与原代码的两处差别

两处都不是算法语义，是实现缺陷：

| 差别 | 原代码 | 本算子 | 理由 |
|---|---|---|---|
| 精度 | h 取整到 1°、s/l 取整到 1%，输出 `int()` 截断 | 全程浮点 | 这层量化平均偏暗 **1.73 码**、最大 **9 码**（`tools/ref_ps_hue_sat.py` 的 breakdown） |
| `saturation=+100` | `s/(1−1)` → `ZeroDivisionError` | 返回满饱和（`s>0` 时） | `x→1⁻` 时 `s/(1−x)→+∞`，钳位后就是 1，取左极限 |

## 公式的合理性

**成立的地方**

1. **明度滑杆不碰色相。** 两个分支都是均匀仿射 `c ↦ k·c + b`，色相只由通道差值之
   比决定，实测 Δh 恒为 0。同时它是单调的、端点精确（+100 全白、−100 全黑）、
   不溢出 —— 比「直接改 HSL 的 L」在亮端会硬顶成白色要稳。
2. **端点干净。** −100 精确到中性灰，+100 精确到满饱和，两个方向都收敛到有意义的
   颜色，没有反相或跳变。
3. **顺序符合直觉。** 先定调子（明度），再定色彩强度（饱和度），且饱和度看到的是
   提亮后的 S，避免了「先加饱和再提亮导致过曝」的常见问题。
4. **无越界路径。** HSL→RGB 天然保色域，S 钳到 [0,1]，任何参数组合都不会输出非法值。

**不成立的地方**

1. **正支刻度与标签不符。** 正向乘数是 `1/(1−x)`，不是 `1+x`：`+25` 实际是 ×1.33
   （+33%），`+50` 是 ×2（+100%），`+90` 是 ×10。负支才是名副其实的百分比
   （`−50` 就是 ×0.5）。同一根滑杆左右两侧的量纲因此不对称。
2. **正支有「悬崖」，会丢层次。** `s ≥ 1−x` 的像素一律钳到 100：`+50` 时原 S≥50%
   的一半像素塌成同一个值，`+100` 时所有彩色像素统一满饱和，等价于把饱和度二值化。
   表现为平坦色块与色带。
3. **明度对 S 的影响强烈不对称。** `+60` 会把 `(100,30,10)` 的 S 从 82% 压到 23%，
   而 `−60` 一字不动（82%）。用户预期「只改明度」，实际提亮会明显掉饱和、发灰。
4. **HSL 的 S 不是感知量。** 同一 S 在黄色与蓝色上的视觉强度差很多，所以同一档位
   在不同色相上表现不一致。这是 HSL 模型的固有问题，本公式无法规避。
5. **量化损失（原代码）。** 1% 的 s/l 台阶单这一项就有最大 8 码、平均 −1.25 码的
   偏差，且系统性偏暗 —— 这是 8 位整数实现的代价，不是算法的一部分。
