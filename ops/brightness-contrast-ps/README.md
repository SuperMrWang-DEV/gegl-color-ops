# lb:brightness-contrast-ps · Brightness/Contrast (Photoshop)

按实测逆向出来的 Photoshop「亮度/对比度」，**新版与旧版（对话框里的「使用旧版」）两套行为都在里面**。
同一张标定图分别过 PS 26.10 和本算子，逐像素对比见文末「验收」。

- GEGL id：`lb:brightness-contrast-ps`
- 菜单：`Colors → SuperMrWang → Brightness/Contrast PS`
- 类型：`GeglOperationPointFilter`（逐像素，无邻域）
- 参数：`brightness`（−150…150）、`contrast`（−50…100）、`legacy`（默认关＝新版）

## 先看一条结论：它就是一条逐通道相同的 LUT

标定图里放了灰阶 ramp、反向 ramp、R/G/B 单通道 ramp 和全色相环，实测：

- 三通道走**同一条**曲线（通道耦合 0.000）；
- 正/反向 ramp 逐位镜像（无位置依赖）；
- 全色相环过完曲线后色相会漂（旧版 c=100 时最大 50°）—— 这恰恰说明它是逐通道
  LUT，而不是在 Lab 明度上做文章。

所以两个版本都能简化成一维映射 `f(x; b, c)`。

## 两个版本的结构

| | 新版（`legacy=false`） | 旧版（`legacy=true`） |
|---|---|---|
| 亮度 | 非线性曲线族，x=0 与 x=255 固定 | `clamp(x + b)`，**b 先夹到 ±100** |
| 对比度 | 围绕 **128** 的 S 曲线，两端压缩 | 围绕 **89** 的线性缩放，K 见下 |
| 组合顺序 | 先亮度 → 后对比度 | c>0：先亮度后对比度；c<0：反过来 |
| 纯白 | b>0 曲线自然收在 255；b<0 时 x=255 强制 255 | 无此规则（255 照样被压） |

旧版闭式（实测精确到 0.13 码）：

```
bb = clamp(b, -100, 100)
c > 0 : out = clamp(89.00 + (x + bb - 89.00) / (1 - c/100))     ← b 也被 K 放大
c < 0 : out = clamp(89.00 + (x - 89.00) * (1 + c/100) + bb)     ← b 不被缩小
c = 0 : out = clamp(x + bb)
K 的两种写法 = 1/(1-c/100) 与 1+c/100，实测吻合到 1e-4
```

**对比度的支点不是 128 而是 89.00**（= 255 × 0.349），这是旧版最反直觉的一处：
c=50、b=0 时 128 → 167，中灰会被推亮。这一点用 31 条曲线做公共不动点最小二乘得到，
不同 c 之间一致性在 ±0.03 码内。

新版没有闭式，用两张一维表：亮度族 61 档（b 步长 5）、对比度族 31 档（c 步长 5），
每档一条 255 点曲线，参数方向与 x 方向都线性插值。表由
`tools/gen_bc_tables.py` 从 `bc-cal/bc_model.json` 生成，算子不手抄常数。

## 为什么新版要查表

新版亮度的低值段是**严格的线性**：`f(x) = k·x`，其中 `k = exp(0.00630126·b)`
（b=+50 → 1.3705，b=+100 → 1.8782，b=−150 → 0.3887，61 档对数残差 8e-5）。

后来把结构拆开了（见 `bc-cal/RESULTS.md` 第五节之二）：

- **b>0**：线性一直延伸到 `k·x ≈ 128`，之后接一段**三次肩部**，切线连续，末端收在
  (255, 255)。b ≤ 100 时这段拟合残差只有 0.03 码；b>100 时三次不够（b=150 差 3 码），
  四次降到 0.7 码。
- **b<0**：不是三次，而是**正向曲线的反函数**（`f₋ᵦ = fᵦ⁻¹`，平均误差 0.01 码）。
  所以「b<0 在中高段上拱」只是同一条压缩曲线翻过来看，没有第二套机制。

闭式版本在 `bc-cal/bc_compact.py`（每档只存 4 个数，负向求逆）。算子仍然保留实测表，
原因只有一个：最靠近白的十几个像素处正向斜率只有 0.02，求逆会放大 50 倍，闭式在那里
有 3 码误差，而实测表是 0 码。表由 `tools/gen_bc_tables.py` 从 `bc-cal/bc_model.json`
生成，算子不手抄常数。

## 性能

b、c 对整张图是常量，所以整条复合曲线在 `prepare()` 里折成一张 256 项 LUT，
`process()` 每个通道只剩一次查表 + 一次 lerp。全图 256×192 渲染约 0.2 s（含 PNG 编解码）。

## 验收

`python tools/check_bc_ps.py` —— 用 gegl CLI 渲染标定图，和 PS 的 16 位导出逐像素比：

| 版本 | 参考图数 | 中位偏差 | 95% | 最大 |
|---|---|---|---|---|
| 新版 | 154 | 1 码 | 1 码 | **2 码** |
| 旧版 | 154 | 0 码 | 1 码 | **1 码**（c=100 见下） |

这 1 码基本是「PS 16 位导出 ÷257」与「gegl 8 位 PNG 输出」之间的舍入，不是模型误差。
Python 参考实现 `bc-cal/bc_ref.py` 直接对 16 位数据回放，新版残差 0.5 码、旧版 0.09 码。

## 已知偏差

1. **旧版 c=100**：PS 在支点 x=89 上输出 159（K 发散时 `0×∞` 的产物），本算子按极限
   输出 0/255。只影响恰好等于 89 的那一列像素，其余全部一致（95% 分位 0 码）。
2. **新版的 255 特例**：b<0 时实测 254 照曲线走（b=−150 时 214），255 却原样保留 255 ——
   单纯白保护（b>0 时曲线本来就自然收在 255，不需要这条）。本算子照抄这一行为；
   不想要可以在上游 `bc_ref.py` 里去掉。
3. 参数取非整数时（例如 b=7、c=43）误差会升到 0.6 码左右，因为表按步长 5 建。
   要更细就把 `bc-cal/batch_bc2.jsx` 的步长改小重跑。

## 与 `lb:hue-saturation` / `lb:exposure` 的关系

那个是把亮度当 HSL 的 L 或 EV 处理，卷的是色彩模型；这个只忠实复刻 PS 的两条曲线。
需要"和 PS 对得上"就用这个，需要"调得好看"用别的。
