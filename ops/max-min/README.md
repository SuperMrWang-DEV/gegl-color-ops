# lb:max-min · 最大值 / 最小值

两个方向、四个参数、一份在缓冲自身精度里跑的滑动极值。下面从「GIMP 为什么已经没有
它」讲起，再讲算法、精度、边界，最后是验证方法与实现里踩过的两个坑。

```
        ┌─────────────┐               ┌─────────────┐
输入 ──▶│ 取邻域最大值 │──▶ 亮区外扩   │ 取邻域最小值 │──▶ 亮区收缩
        └─────────────┘               └─────────────┘
```

最大值把亮区往外推、吞掉暗处的小点；最小值反过来收亮区、啃掉抠图残留的白边。
蒙版精修、去灰尘点、发光底图、做描边都用它。

## GIMP 里为什么得自己写

GIMP 2.10 之前有「滤镜 → 通用 → 膨胀 / 腐蚀」，之后交给 GEGL 的
`gegl:dilate` / `gegl:erode`。这两个属于 GEGL 的 **workshop 算子**，官方 Windows
构建没有把它们编进来：

```
$ gegl --list-all | grep -E "dilate|erode"      # 空
$ 查 PDB plug-in-dilate                          # None
$ strings libgegl-0.4-0.dll | grep gegl:dilate   # 空
```

本机 GIMP 3.2.8 上确认三条都为空。剩下的只有 `gimp-selection-grow` /
`-shrink`，但它们只作用于**选区**，改不了一张蒙版或一个图层的像素。

所以这个算子不转调任何原生过程，是自己算的——这也是本项目里为数不多的
「不能拿原生当基准」的算子，好在形态学的定义是完全确定的，见下面的验证。

## 参数

| 参数 | 范围 | 说明 |
|---|---|---|
| `mode` | `maximum` / `minimum` | 最大值（膨胀）/ 最小值（腐蚀） |
| `radius` | 1–100 | 邻域半径**像素**。r=1 即 3×3，边缘向外长一圈 |
| `shape` | `square` / `round` | 方窗 (±r, ±r)；圆盘 r。对应 PS 的方形度 / 圆度 |
| `affect-alpha` | 布尔，默认关 | 关掉时 alpha 原样透传（PS 同样不动图层透明度） |

**半径语义与 Photoshop 一致**：r 表示检查 `(±r, ±r)` 的邻域，不是窗口边长。
所以 r=1 得到的正是 3×3，而不是 2×2。

圆盘结构元用 `dx² + dy² ≤ r²` 判定，等价于逐行取半宽 `⌊√(r²−dy²)⌋`：

| r | dy=0 | dy=±1 | dy=±2 | dy=±3 |
|---|---|---|---|---|
| 1 | 1 | 0 | — | — |
| 2 | 2 | 1 | 0 | — |
| 3 | 3 | 2 | 2 | 0 |

## 算法

**方窗可分离**：二维方窗的极值 = 先横向取一次、再纵向取一次，两遍都是一维
滑动极值。一维用 **van Herk / Gil-Werman**：按窗口宽度分块，块内先算前缀与
后缀极值，任意一个窗口恰好被「起始处的后缀 + 末端处的前缀」拼满，每像素两次
比较。总复杂度 **O(n)，与半径无关**。

**圆盘不可分离**（每行半宽不同），退化为逐 `dy` 做横向极值、再纵向累积，
**O(n·r)**。半径 100 时的比较次数约为方窗的 100 倍，但极值只有比较没有乘法，
3MP 图仍在秒级。

实测（3.0 MP，u8 RGB，单线程）：

| 形状 | 半径 | 耗时 |
|---|---|---|
| 方窗 | 1 | 13 ms |
| 方窗 | 100 | 43 ms |
| 圆盘 | 10 | 63 ms |
| 圆盘 | 100 | 1.26 s |

方窗 r=1 与 r=100 只差 3 倍，正好印证复杂度与半径无关。

## 精度：三个类型各展开一份

极值只需要大小关系，但**结果值必须原样搬出来**。所以 `maxmin-kernel.h` 是一份
模板头文件，被 `max-min.c` 以不同的 `PLANE_T` 宏包含三次，生成 u8 / u16 /
float32 三份同构代码：

```c
#define PLANE_T     guint8
#define PLANE_BAND  band_u8
#include "maxmin-kernel.h"
```

缓冲是什么精度就在什么精度里比较，中途**不做任何格式转换**。把 u16 读成 float
再写回，个别像素会差 1 码——这里不给它机会。同理不做色彩管理、不做 gamma 换算：
PS 的这两个滤镜也是直接对通道值取极值，跟着它的语义走，彩色图上才会得到一样的
偏色。

## 边界

画布外按**复制边缘像素**处理。对取极值而言，这与「只算窗口内的那部分」**逐位
等价**：补进来的永远是边缘那一列 / 那一行的副本，而那一列本来就在窗口里，
不引入任何新值。所以不像模糊那样会在边缘暗一圈，也不需要额外的边界策略参数。

## 逐通道

三个色 / 灰度分量各自独立取极值，**alpha 默认不参与**。这是 PS 的语义：滤镜
不改图层透明度。要连 alpha 一起算，把 `affect-alpha` 打开。

彩色图上因此会出现偏色（红蓝交界处冒紫边），这不是 bug，是逐通道运算的必然
结果。要没有偏色就换成单色目标：蒙版、通道、灰度层。

## 正确性验证

本机没有可对照的原生实现，所以基准写成 **O(r²) 的四重循环**（`tools/check_max_min.py`
里的纯 Python `brute()`）——和 van Herk 是两条完全独立的代码路径：

```
python  tools/check_max_min.py   # 在 GIMP 的 python-fu 里跑，见文件头
```

27 项，覆盖：

- u8 / u16 / float32 三种缓冲精度，**逐字节 / 逐位相同**
- 方形与圆形 × 最大值与最小值 × 半径 1 / 2 / 5
- 单通道 `Y u8`（蒙版的主战场）与 RGBA
- alpha 默认不动 / `affect-alpha` 开
- 图边缘（暴力实现同样钳位，两者必须一致）
- 高 301 px 的图跨过 128 行的分带边界，验证拼接无接缝
- 半径 100 在 9×7 的小图上（窗口比图还大）
- 先最小后最大 = 开运算：孤立亮点被抹掉、方块保形
- 2000×1500 的性能抽样

插件层另有 `tools/check_max_min_plugin.py`（12 项）：过程注册、非破坏滤镜挂载、
蒙版走写像素、图层组拒绝、半径越界被参数校验挡住。

## 分带实现的一个坑

输入按 128 行一带读，横向余量 `r` 列、纵向余量 `r` 行，四个通道在同一带里一起
算完才写回。**通道循环必须在分带循环内部**：反过来写，后一个通道会用输入重建
整带，把前一个通道的结果覆盖回去——第一版就是这么错的，六项 u8 用例全挂，
单通道（只有一路）反而全过，很容易看漏。

另一处：列方向的暂存区容量要按 `max(pw, ph)` 算。只按宽度 `pw` 分配，在「高瘦」
的分带上会越界写（已踩过一次，表现为跑完若干用例后进程崩掉）。
