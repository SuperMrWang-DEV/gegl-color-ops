the classic editor's **Brightness/Contrast**, matched by black-box measurement. **Both the
current and the legacy behaviour** (the "Use Legacy" checkbox in the dialog) are in
here. The same calibration chart was pushed through the classic editor 26.10 and through this
operator and compared pixel by pixel; see the acceptance numbers at the end.

- GEGL id: `lb:brightness-contrast`
- Menu: `Colors → SuperMrWang → Tone → Brightness/Contrast`
- Type: `GeglOperationPointFilter` (per-pixel, no neighbourhood)
- Parameters: `brightness` (−150…150), `contrast` (−50…100), `legacy` (off = current)

## First, one conclusion: it is a LUT, identical for every channel

The chart holds grey ramps, inverted ramps, single-channel R/G/B ramps and a full
hue wheel. Measurements:

- the three channels follow **the same** curve (channel coupling 0.000);
- forward and inverted ramps mirror bit for bit (no positional dependence);
- the hue wheel drifts after the curve (up to 50° in the legacy version at c=100) —
  which is exactly what proves it is a per-channel LUT rather than something acting
  on Lab lightness.

So both versions reduce to a one-dimensional map `f(x; b, c)`.

## Structure of the two versions

| | Current (`legacy=false`) | Legacy (`legacy=true`) |
|---|---|---|
| Brightness | a family of non-linear curves, x=0 and x=255 pinned | `clamp(x + b)`, with **b clamped to ±100 first** |
| Contrast | S-curve around **128**, both ends compressed | linear scaling around **89**, K below |
| Order | brightness, then contrast | c>0: brightness then contrast; c<0: the reverse |
| Pure white | with b>0 the curve naturally ends at 255; with b<0, x=255 is forced to 255 | no such rule (255 gets compressed too) |

Legacy closed form (agrees with measurement to 0.13 code values):

```math
b' = \operatorname{clamp}(b,\,-100,\,100),\qquad
\text{out} = \operatorname{clamp}\bigl(89 + K\,(x-89) + \beta,\ 0,\ 255\bigr)
```

```math
(K,\ \beta) = \begin{cases}
\left(\dfrac{1}{1-c/100},\ \dfrac{b'}{1-c/100}\right), & c > 0 \quad (b \text{ is scaled by } K) \\[12pt]
\left(1+\dfrac{c}{100},\ b'\right), & c < 0 \quad (b \text{ is not scaled}) \\[10pt]
\bigl(1,\ b'\bigr), & c = 0
\end{cases}
```

The two ways of writing $K$, $1/(1-c/100)$ and $1+c/100$, agree to $10^{-4}$.

**The contrast pivot is not 128 but 89.00** (= 255 × 0.349). This is the most
counter-intuitive part of the legacy version: at c=50, b=0 an input of 128 becomes
167, i.e. mid grey is pushed brighter. It came out of a least-squares search for
the common fixed point over 31 curves, consistent across c to within ±0.03 code
values.

The current version has no closed form. It uses two one-dimensional tables: 61
brightness steps (b in steps of 5) and 31 contrast steps (c in steps of 5), each a
255-point curve, interpolated linearly in both the parameter and x direction. The
tables are generated by `tools/gen_bc_tables.py` from `bc-cal/bc_model.json`; no
constants are copied by hand.

## Why the current version needs tables

The low end of current-version brightness is **strictly linear**: `f(x) = k·x` with
`k = exp(0.00630126·b)` (b=+50 → 1.3705, b=+100 → 1.8782, b=−150 → 0.3887; log
residual 8e-5 over 61 steps).

The structure came apart later (see section 5.2 of `bc-cal/RESULTS.md`):

- **b>0**: the linear part runs to `k·x ≈ 128`, then a **cubic shoulder**, tangent
  continuous, ending at (255, 255). For b ≤ 100 the fit residual is 0.03 code
  values; above 100 a cubic is not enough (b=150 is off by 3) and a quartic brings
  it to 0.7.
- **b<0**: not a cubic but the **inverse of the positive curve** (`f₋ᵦ = fᵦ⁻¹`,
  mean error 0.01). So "b<0 bows upward in the midtones" is the same compression
  curve seen backwards — there is no second mechanism.

A closed form exists in `bc-cal/bc_compact.py` (four numbers per step, inverted for
negative b). The operator still ships the measured table for exactly one reason:
the positive slope near white drops to 0.02, inverting amplifies that 50×, and the
closed form is off by 3 code values there while the table is off by 0. Same tables,
generated by `tools/gen_bc_tables.py`.

## Performance

b and c are constant over the image, so the whole composite curve is folded into a
256-entry LUT in `prepare()`; `process()` is one table lookup plus one lerp per
channel. A full 256×192 render takes about 0.2 s including PNG encode/decode.

## Acceptance

`python tools/check_bc_ps.py` renders the chart through the gegl CLI and compares
it with the classic editor's 16-bit export, pixel by pixel:

| Version | Reference images | Median | 95% | Max |
|---|---|---|---|---|
| Current | 154 | 1 code | 1 code | **2 codes** |
| Legacy | 154 | 0 codes | 1 code | **1 code** (c=100, see below) |

That one code is mostly rounding between "the classic editor 16-bit export ÷257" and "gegl 8-bit
PNG output", not model error. The Python reference `bc-cal/bc_ref.py` replays the
16-bit data directly: current-version residual 0.5 code, legacy 0.09.

## Known deviations

1. **Legacy c=100**: the classic editor outputs 159 at the pivot x=89 (the product of
   `0×∞` as K diverges); this operator takes the limit and outputs 0/255. Only the
   column of pixels exactly at 89 is affected, everything else agrees (95th
   percentile 0 codes).
2. **The 255 special case in the current version**: with b<0, 254 follows the curve
   (214 at b=−150) but 255 stays 255 — plain white protection (with b>0 the curve
   already ends at 255, so the rule is not needed there). The operator copies this
   behaviour; drop it in `bc_ref.py` upstream if you disagree.
3. With non-integer parameters (b=7, c=43 for instance) the error rises to about
   0.6 code values, because the tables are built in steps of 5. For finer results,
   shrink the step in `bc-cal/batch_bc2.jsx` and re-run.

## Relation to `lb:hue-saturation` / `lb:exposure`

Those treat brightness as HSL lightness or as an EV stop, i.e. they twist the colour
model. This one only reproduces the classic editor's two curves. Use it when you need to
match the classic editor; use the others when you want it to look good.
